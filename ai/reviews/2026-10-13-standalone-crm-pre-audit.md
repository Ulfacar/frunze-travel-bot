## Smallest safe implementation contract

1. **Dedicated web service.** Reuse reviewed domain services and native templates behind a separate startup/configuration/security boundary. Public routes are only a minimal non-sensitive health endpoint, login and necessary local assets; authenticated CRM routes are explicitly enumerated. API docs/openapi and all webhook/send/bot-control endpoints are absent or denied. Default-empty source/legal/calendar/storage authorities remain empty unless separately and explicitly approved. A deployment flag must not synthesize such authority.
2. **Live authenticated subject.** Use a new high-entropy service-specific signing secret and unique host-only Secure/HttpOnly cookie, explicit lifetime and SameSite setting, with no parent-domain cookie. Login resets prior session state/CSRF material; replay of a revoked/changed-account cookie is denied. Preserve named-actor, owner, application and full-admin gates. New roster entries must not silently become administrators through reserved names. No demo-password bypass in private mode. Authentication failure must never fall through to a default manager.
3. **Request perimeter.** Exact allowed host/origin and restricted proxy trust; reject unexpected Host/forwarded-host/origin combinations and oversized/malformed bodies before native operations. Apply no-store to authenticated pages and sensitive errors, no-referrer, nosniff and anti-framing controls. Existing inline/native behavior must still work with any CSP. Current base loads HTMX from unpkg and legacy fonts from Google; prefer packaged same-origin assets for a self-contained private release and verify browser behavior without external CDN availability.
4. **No external effects.** No provider secrets, bot registry with live channels, scheduler or sender initialization. Independent network isolation/egress restriction is a second barrier, not a substitute for route and execution controls. Test providers/LLM/queue/scheduler with fail-on-call sentinels and exercise both successful CRM operations and blocked legacy routes. Internal tasks remain internal and cannot acquire an outbound recipient or delivery claim from standalone setup.
5. **Separate persistence.** New Postgres service/role/database/volume, no published DB port, no existing bot mounts/networks, and an explicit private environment source. Persistent storage must survive application replacement/restart. A failed bootstrap aborts startup; retry converges without duplicate products/users/seed records. Distinguish live process health from ready schema/assets and usable authenticated flow. Avoid logging the DSN, passwords, signed forms, cookie or person data in diagnostics.
6. **Exact deploy artifact.** Record reviewed Git/overlay identities, built image digest and actual installed dependency/runtime identity. Build/test and deploy the same image, not an uncontrolled rebuild of floating dependencies. Non-root app, no Docker socket/host filesystem mount or privileged mode; only necessary write locations. Confirm memory/disk/request limits fit ordinary and bounded quarantine operations without silently lowering domain recovery reserves.
7. **Reversible release.** Before exposing the new hostname, record old bot container/image/port/health identity read-only, new service ownership and proxy target, new database backup/restore command and rollback image. On failure, remove only the new route or stop/replace only the new app; preserve the new database volume and all old services. Never use `down -v`, bulk prune or forced schema downgrade as rollback. Existing migrations deliberately refuse populated inverse transitions. Test fresh restore and original retry on the new image; a current local Windows COPY test alone is not the deployed Linux backup proof.

No new auth framework, external login service, Redis deployment or provider integration is inherently required. A small standalone wrapper with explicit validators, constrained routes, current-account session validation, dedicated bootstrap and compose can satisfy the contract. If implementing the wrapper changes shared auth/task behavior, the exact changed boundary needs its relevant compatibility checks.
