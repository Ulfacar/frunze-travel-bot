## Concrete pitfalls and required acceptance

1. **P1 risk: accidental contact inheritance or mixed-person calculation.** `entry_storage._contact/_history/save_stay_history` and `entry_calculations._sources/save_calculation` are contact-scoped. `kg_entry._context` automatically selects the payer's latest `StayHistory`; it is unsuitable for this flow, including a primary applicant. `applicant_profiles._sources` deliberately passes no history. Use only the new case/applicant journal and composite parent/predecessor references. Accept: two applicants sharing a payer/case have independent empty/current/historical states; another person's history ID, wrong case and contact history IDs cannot attach. No history row means missing evidence, not a complete empty history.

2. **P1 risk: a one-row check presented as a valid journal.** Contact `_history` checks one snapshot and its interval projection; it does not validate the whole predecessor chain. Follow the bounded full-chain approach in `applicant_profiles._history`: contiguous revisions, strictly preceding IDs, scope, hashes, actor-bound command, previous ID/hash, canonical payload size, and a limit-plus-one fetch. Add both SQL constraints and the model's immutable/bulk-write guard registration (`models.ENTRY_IMMUTABLE_MODELS`); frozen JSON alone is insufficient. If interval rows are projected, validate every projection and confirmation stamp against the parent snapshot. Accept raw-SQL corruption, skipped/forked/cross-person predecessors, altered projections, ORM/bulk mutation and read-time overflow rejection. Keep historical pins readable by resolving the originally pinned profile, not requiring every old row to equal the latest profile.

3. **P1 risk: incomplete clock validation or broken retries.** `_normalize_history` verifies interval dates against the submitted `as_of`, but does not reject a future `as_of` against the server clock. Apply that new-write check after case/applicant locks using the existing Bishkek day convention. Do not change this shared helper's historical contact semantics incidentally. Backdated corrections must not make latest revision synonymous with current confirmed evidence; define a conservative stale state rather than silently carrying newer confirmation backward. Exact matching retry must resolve the original command before current-profile/date/CAS/capacity conditions reject a new write. Contact storage omits actor from its request hash; use the actor-bound applicant command pattern instead. Accept delayed retry after another edit, profile change, day change and journal capacity; conflicting actor/body/key and stale CAS must fail without writes. Lost commit acknowledgement must retain the same retry key/body and recover the original receipt.

4. **P1 risk: opaque token mistaken for passport continuity.** `HISTORY` accepts a nullable 32-hex `passport_ref`. Profiles contain passport country/type/expiry, but no current passport identity. Issued-document `passport_fingerprint` uses 64 hex characters and application-local passport revisions: these are not interchangeable identities. Define an explicit current opaque reference plus pinned profile ID/hash for the new evidence, with conservative staleness on a newer profile and explicit reconfirmation. Never infer sameness from country, expiry, payer, applicant role, revision number or repeated display label; never truncate a 64-character fingerprint into this field. Unknown reference remains unknown. A well-shaped token alone proves neither document verification nor permission to collect raw numbers; native controls should guide opaque-reference use and accept no extra number/upload field. Accept same/different/null tokens, changed passport with same country, new profile after save and foreign-person reference reuse without inferred continuity.

5. **P1 risk: arithmetic output mistaken for confirmed eligibility.** The normalizer rejects confirmed `client_statement` and contradictory open intervals, but permits `history_complete=null/false`, unknown basis/country/reference and unconfirmed rows. Preserve those values and display them explicitly; do not default unchecked completeness to true or generate confirmation stamps from GET/rendering. An explicitly complete empty history is distinct from absence. Closed interval overlap is intentionally accepted by the existing union-based arithmetic; do not silently deduplicate/rewrite factual records or invent a new legal rule. `StayDayReview` can produce `computed_scenario` while retaining `history_incomplete`, `history_unconfirmed`, passport/basis review findings and unapproved policy flags. Therefore future integration must inspect findings/authority, not merely arithmetic status. Saving this journal must leave eligibility, quote, regime selection and delivery untouched.

6. **P1 risk: torn read or lock inversion in later integration.** `applicant_profiles._subject` does not itself lock the case: its call to `applications._case` uses the default `lock=False`. E6-27 must explicitly establish case then applicant locking, as current `approved_qualification.propose_route` does, rather than assuming the helper supplies both. The internal reader should accept the existing session/verified subject context, validate the entire bounded journal and return immutable IDs/hashes plus evidence status. It must not open a second transaction, call the contact calculator or acquire a new parent lock after a publication-set lock. Return a pinned snapshot for subsequent calculation, never a separately loaded latest row. Accept PostgreSQL competing writers and a reader held across a blocked write, plus SQLite's explicit transaction behavior from `applications._run`.

7. **P2 risk: bounded domain data silently truncated by the native form.** The contact form parser is qualification-specific: 65,536 encoded bytes, 384 fields and a fixed allowlist. `HISTORY` allows 1,000 intervals; copying those form limits/controls directly can make valid saved history impossible to round-trip. Define matching domain/encoded-body/field-count limits or explicit bounded editing that preserves every undisplayed row. Reject duplicate/unexpected fields and forged scope/revision/profile/reference metadata; never clear rows because controls were omitted. Keep actor/session CSRF and case/applicant signatures, feature/full-admin/workday gates, no-store headers, escaped echo and original retry envelope on errors. Accept RU/EN current/history views, maximal supported input, unchanged save, 409/422/503 recovery, mobile, no-JS and print. A historical version must remain visibly historical and cannot overwrite current state without CAS.

8. **P2 risk: capacity or migration loses the correction path.** Fix count and canonical-byte limits before implementation. At either limit, reads and exact retries must still work, partial new rows must roll back, and operators must receive an explicit capacity result. Decide how later discovered uncertainty is represented without leaving a capped history silently usable as current evidence. Reuse the additive profile migration's composite constraints and populated-downgrade refusal, including the PostgreSQL table lock / SQLite transaction guard; do not copy or convert old contact/profile records. Accept actual migrated SQLite foreign keys and loopback PostgreSQL constraints, empty downgrade, populated refusal, rollback and old-table/receipt preservation.
