## Concrete hazards in the installed implementation

1. **Logical bot/user identity is not the provider destination.** `Orchestrator._key` (`orchestrator.py:171`) uses logical bot plus `Message.user_id`; actual send (`:595`) uses `Message.chat_id`. Telegram sends `chat.id`, which differs from `from.id` in groups. Bitrix sends `DIALOG_ID`, not `FROM_USER_ID`. A guard keyed by the legacy conversation key alone can miss the actual recipient.
2. **The canonical shadow is not proof of an exact route.** `shadow_bridge.py:42–58` and `messaging_shadow.py:41–45` create Dialog using normalized phone for every channel. Some identities are skipped; others can be transformed. `DialogService.get_or_create` (`services.py:124`) can return an existing row by channel/bot/key and does not itself prove the caller's proposed contact matches it. Bind service must independently validate actual Dialog contact and transport provenance. Do not reinterpret an arbitrary existing numeric Telegram/Bitrix shadow key as an authenticated provider chat ID.
3. **Logical account aliases can bypass a stop.** Wappi uses the resolved profile and provider endpoint (`wappi.py:328–334`), including a global fallback. Telegram main has both a global adapter and per-test-bot tokens (`main.py:166–176`); generic manual outbound selects the global Telegram adapter. Bitrix uses portal configuration and provider BOT_ID (`bitrix_openlines.py:86–124`). Two logical bot IDs can designate the same provider account; keying locks/bindings only by logical bot ID creates two locks for one real destination.
4. **Reply and followup are independent send paths.** `_reply` directly invokes the adapter; `_send_followups` (`followup.py:130–156`) uses `outbound.send_to_client`. `run_manual` also calls that automated batch sender, so the button-triggered batch needs the same guard. Generic outbound additionally carries authenticated human replies and staff alerts; blanket guarding it as autonomous would change unrelated behavior.
5. **Legacy handoff is mutable and not E6-12 ACK.** `intercept.py:43` can expire interception. Orchestrator may send an additional waiting acknowledgement after legacy handoff (`:480–503`). `instant_handoff` records notification attempts and sends manager/CC messages; delivery is not manager acknowledgement. `runner.py`'s handoff tool changes legacy stage. None establishes the proposed immutable binding/card guarantee.
6. **The public interview command owns a transaction.** `entry_interviews.record_action` (`:300–325`) calls retrying `_run`. Calling it and then separately inserting a binding can commit a handoff without its stop or vice versa. Calling provider code inside the same retrying helper can invoke the provider again after a database exception.
7. **Suppressed sends currently have success side effects available.** `_reply` logs pending with `counts_as_reply` before provider invocation, then marks sent and mirrors the text. Its callers may tell `instant_handoff` that the reply was promised/sent. Followups increment count/stage and Bitrix touch after generic outbound returns. A guard that returns `None` on suppression would look like a successful Telegram/Bitrix send and preserve those false effects.

## Smallest safe design

### Exact transport identities and activation boundary

Use one server-owned canonicalization/resolution function for enrollment, lock keys, lookups and actual sends. Capture the resolved adapter/transport identity once and invoke that same adapter; do not resolve a second potentially different account after the check. Persist a versioned non-secret descriptor and its digest. Never persist tokens or secret-bearing webhook URLs in policy/binding metadata.

| Channel | Required identity and safe scope |
|---|---|
| WhatsApp/Wappi | Provider account/profile plus exact private recipient digits. Canonicalize only proven equivalent provider spellings such as digits versus the adapter's `@c.us` suffix. Do not apply Kyrgyz phone guessing, strip arbitrary punctuation, collapse groups into a person's phone or infer `@s.whatsapp.net` support that this sender does not implement. Reject group/unsupported recipient forms in the first slice. |
| Telegram | Actual configured Telegram bot identity plus exact canonical signed integer chat ID; private/group support must be explicit. Do not use sender user ID, phone normalization or a default-token fallback for a per-bot route. Either establish trusted route provenance for an existing Dialog or refuse enrollment. |
| Bitrix | Portal/account namespace plus provider BOT_ID and exact canonical DIALOG_ID. Preserve supported dialog syntax, including chat prefixes, without numeric/phone coercion. A phone-keyed shadow row does not prove the DIALOG_ID. Refuse ambiguous enrollment. |

There is no need to call providers to discover identities during this task. Validate trusted synthetic configuration and stable non-secret account identifiers. Account aliases must produce the same transport scope or be rejected as ambiguous configuration. Account/configuration identity changes must not silently make an existing binding disappear from the stop logic.

If trustworthy Telegram/Bitrix route provenance requires a separate mapping feature, implement the complete first slice for validated Wappi private routes and explicitly reject unsupported enrollment. Keep the other channel requirements/coverage UNKNOWN. Do not create a misleading cross-channel guarantee just because all adapters call a common Python helper.

**Narrow option accepted by the builder after this assessment:** the initial complete scope is bound WhatsApp private Dialogs. Account identity comes from the actual captured Wappi adapter's provider base and profile, not logical bot ID; aliases for that physical account share a latch and lock. Accept only digits with the optional supported `@c.us` form. Telegram/Bitrix enrollment remains unavailable until separately evidenced route mapping exists. Validate provider base metadata so no userinfo/secret-bearing query or token is persisted. This narrower integration remains useful and testable without inventing recipient policy.

The deployment guard allowlist is separate from the authority/privacy policy. Both start empty. Within an activated account, malformed identity, ambiguous account resolution, missing schema, failed database read or corrupt routing information means no autonomous provider invocation. Invalid allowlist configuration must not silently parse as an empty list and restore legacy behavior. Accounts conclusively outside activation retain existing behavior. Removal of an activation scope is an explicit operational rollback, outside this task, and must be described as disabling protection rather than ordinary policy expiry.

### Atomic permanent stop and pinned handoff

The binding command accepts an existing Dialog ID, exact interview target, signed expected revision/card and request key, never a free-form recipient. The preview displays the exact route and permanent effect; server save rereads/revalidates it. Validate current existing full-admin identity, policy actor/account scope, case contact, applicant/interview owner/card, route provenance and policy validity at the stored timestamp. Binding a payer/contact's route grants no permission to disclose applicant facts there.

For active/paused interview, append the handoff and binding in **one** transaction. Extract a session-owned `record_action` primitive while preserving the public wrapper's authorization/validation/retry contract; do not duplicate the reducer or call a nested public transaction. For an already pending/acked interview, bind its exact existing card and preserve history. One competing action/revision may win; rollback of either write leaves neither new handoff nor binding. Retry returns the original receipt after current policy removal, provided the caller is still authorized. Conflicting keys/targets fail.

Reuse the existing exact owner/card-hash ACK with current full-admin checking. Do not assign a new owner, expand manager access, send notifications or treat delivery as acceptance. ACK, source-policy expiry, restart, new interview and legacy “return to bot” do not clear this latch. Revoking owner access may make ACK unavailable; it must not enable bot replies.

The immutable binding pins the handoff event/card, interview/case/applicant/contact/Dialog, route descriptor, policy/authority, actor and request. Use scoped foreign keys and immutable guards. Current views may add a separate bound-stop status; never rewrite the historical E6-12 `channel_suppression='not_integrated'` field or its hashes. All other channels of the contact and old unbound handoffs remain explicitly unbound.

Lookup the permanent stop by its pinned transport identity, independent of mutable Dialog fields and current policy. Any applicable binding is sufficient to deny a send; an old card need not remain operationally usable to keep the route stopped. Binding another interview cannot reset the route. If multiple records can reference a route, any one keeps it stopped; otherwise report an existing stop as such instead of pretending a new card was bound.

**Negative lookup integrity needs explicit treatment.** A lone `WHERE transport_key = requested_key` plus hash validation of found rows cannot detect a corrupted routing column moved away from that key: it returns “unbound” and sends. Use a validated immutable routing index/manifest or bounded registry validation sufficient to establish the negative answer; test key/recipient/account columns against pinned payloads, not just snapshot corruption in an already-found row. A fail-closed bound on that validation is preferable to silently permitting unknown state. Hashing is not protection against an attacker able to replace/delete the entire database and every trust anchor; do not claim that stronger threat model.

The builder selected bounded validation of **all binding rows** before a negative answer, with an explicit global cap. This closes the moved-routing-column lookup gap without adding another projection. Corrupt registry or overflow therefore blocks all activated scopes; document that intentional availability cost. Serialize the global capacity check among concurrent binding writers as well as taking their route locks, so two different routes cannot both consume the last slot. A full registry must still permit read, suppression and exact retry; it only rejects new bindings. Never ignore excess rows to stay within the cap.

### Serialization and provider invocation

- Obtain a deterministic advisory lock keyed by the canonical transport scope **before querying for a binding**. Use a stable cryptographic mapping with a namespace, not process-random Python `hash()`. Shared send admission and exclusive binding locks must conflict even when the first binding row does not yet exist. Locking only an existing row does not cover that race.
- Use a single lock order: transport scope, then case/interview/Dialog locks. The sender need not acquire business-case locks. If a writer derives a route from a preliminary read, reread after locking and reject identity changes; never silently switch to an unlocked route.
- Hold the send lock through the bounded callback lifetime, or provide an equally explicit admission protocol. The binder cannot report committed stop while a newly checked send is still waiting to begin. On SQLite, tests must establish a physical writer transaction such as `BEGIN IMMEDIATE` before the empty lookup; do not treat its behavior as evidence for PostgreSQL.
- The sender uses a **non-retrying** transaction/connection lifetime. No provider callback inside `entry_storage._transaction`, `applications._run` or any auto-retry wrapper. A callback is invoked at most once per admitted send operation, including serialization errors, commit/teardown exceptions and cancellation. Never call an unguarded fallback when the guard raises.
- Bound lock wait and provider time. Timeout/cancellation/connection loss after invocation has unknown remote-delivery status and must not trigger automatic re-invocation. Release resources safely, including when cancellation interrupts cleanup. Do not claim exactly-once delivery or the ability to recall a provider request already admitted/in flight; the verified boundary is provider invocation under the functioning lock protocol, not remote display time.
- Unbound valid routes in an activated account still send normally. Suppression is a distinct result, not the provider's ordinary `None` return. Propagate it to callers so no sent marker, reply count, followup increment, touch stage, outbound mirror or “promised reply” is fabricated. Early checks can prevent needless LLM work, but the final check is mandatory for work already running when the stop commits.

### Installed paths and explicit exclusions

Wire the final guarded invocation into orchestrator `_reply` and automated followups, including `run_manual`. This covers greetings, persona/FAQ replies, media fallback, LLM-error fallback and waiting messages only when their actual branches call the guarded `_reply`; test the installed paths. Human replies in `app/admin/router.py:2031,2059` remain authenticated manual sends. `awaiting.py:273`, `watchdog.py:128`, Telegram morning/calendar briefs and instant-handoff manager notifications are staff/operational paths, not a reason to classify generic outbound as entirely autonomous client messaging. Preserve their permissions/routing. Re-run the send-call-site inventory on the final snapshot.

No new client message, confirmation, manager notification, external CRM effect or autonomous consent inference is needed to complete this local stop. Inbound logging and unrelated legacy behavior are separate; this slice does not certify global cessation of all automated CRM actions or prevent every legacy LLM/tool side effect. State that limit.
