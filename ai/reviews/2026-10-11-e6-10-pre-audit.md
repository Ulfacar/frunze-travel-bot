## Actual foundations and constraints

## Smallest safe orchestration model

Prefer **one immutable orchestration journal anchored to a root application/case/person**, carrying an explicit active application and typed dependency roles. This preserves the source process path without coordinating two independently advancing stage journals. The root remains an envelope; neither its procedure nor any child's identity is rewritten. Separate dependent applications must already be explicitly created. A stage transition can link or focus an existing application; it creates no submission/decision/file/payment/message.

Every transition records root identity, previous/new stage, exact edge digest, previous/new active application, dependency role bindings, catalog and execution-policy snapshots/digests, normalized evidence pins, request identity, actor and timestamps. All identities are included in the command hash and retry comparison. A policy separately defines allowed initial codes; arbitrary initial stages such as V20/W19 cannot become a shortcut around earlier evidence. Catalog `kind` stays distinct from the event action: a flag cannot advance the stage cursor, and an exception can only be reached along an explicitly supported edge.

Focus rules must be a small explicit server-owned adapter, never inferred from whichever application happens to be selected in the browser. For example, work decisions before W16 concern the permit, W16–W19 concern the resident application, and W20+ concern registration. U05→U06 must bind the chosen registration or exit application; U06→U07 is unavailable on the registration branch even when some other exit application was approved. These mappings require explicit policy scope and must not be presented as source-law approval.

Represent dependencies as role-qualified links (`permit`, `resident`, `registration`, `protocol`, `exit_visa`, and a separately defined visa role where supported). Each link must match the same case/person and exact required procedure. Reject self-links when a separate procedure is required, duplicate/conflicting roles, unsupported role/procedure pairs and cycles. Pins identify an attempt; do not silently replace it with the newest application or another successful applicant. Retrying a refused attempt uses its explicit `previous_id` successor; cross-procedure dependencies use a different relation.

A bounded stage-event table plus a bounded child table for typed evidence/dependency pins is sufficient. Existing unique keys permit scoped application/package/issued/profile FKs. If evidence uses tagged nullable source columns, enforce exactly the columns required by that source kind; a JSON hash alone is not a relational link. Persist evidence **with** its stage event in one owned transaction. No mutable materialized stage column or universal generic workflow engine is needed.

## Evidence resolver contract

Each required fact is resolved from an explicit fact→role→source mapping for the exact edge. The browser may select an evidence identifier, but cannot choose which source kind can prove an authoritative fact or submit a computed Boolean. Return a typed value, source kind and scope, exact row/revision/hash, source date/reference/proof where that journal has them, freshness semantics and any blocker. Do not manufacture a proof string where an existing journal has only an immutable event/hash/reference.

| Fact family | Minimum safe source and check |
|---|---|
| `consent_confirmed` | Current scoped package consent is `granted`; pin its originating consent event and current state/hash. Missing package/consent is UNKNOWN, not permission for manual fallback. |
| `documents_accepted`, `documents_current`, receiving/resident package facts | Exact role-specific package and current effective acceptance/required document status, with package/policy/catalog hashes and quarantine checks. Receiving a file, a legacy checked row or old approval is not current acceptance. |
| `submission_recorded`, `application_reference_recorded`, `decision` | Validated exact application events/reference for the edge's active procedure. Current decision must match current status; actual submission occurrence and resubmission have explicit ordering semantics. |
| `issued_document_checked`, `delivered_to_client`, `receipt_confirmed`, `exit_visa_issued` | Exact role-specific issued history plus effective quarantine-aware view. Define the required status explicitly; a file hash or an old raw review is not enough. The issued journal currently supports visa/exit visa, so do not reuse it as permit/resident issuance. |
| Actual entry/exit/departure | Exact scoped travel event with direction/date/source/proof/passport. Planned dates never satisfy actual movement. Do not replace unsupported permit travel with another person's visa travel. |
| `profile_complete`, qualification/product facts | Current profile belongs to the applicant, not payer/contact. Explicit completeness criteria and source authority are required; no inference from the presence of a profile row. Draft/unknown qualification cannot be promoted to approved eligibility. |
| `service_payment_confirmed` | Effective same-case ledger evidence and an explicitly authorized payment criterion and case→application applicability. Corrected/voided/refunded amounts, missing FX and unknown contract amount must not become paid automatically. Leave this edge unsupported if that criterion is unresolved. |
| Employer/account/quota, email, external portal payment, official permit/resident issue/collection, police/protocol facts without a suitable authoritative journal | Only an explicit per-fact/per-edge manual-attestation allowlist, with strict source enum, actual date, bounded reference, proof hash, scope and named actor. Never a wildcard fallback for unavailable adapters. These are recorded attestations, not portal operations. |

Manual evidence requires a correction/withdrawal path that appends history. An unknown or false value remains distinct from absent. Proof hashes are identity pins, not proof of truth; policy selects permitted attestation kinds and source-review evidence, and this task configures no actual policy.

Keep **historical validity** separate from **current readiness**. Historical replay uses pinned definitions/policies and exact evidence that was recorded then; expiry or later edits must not make history unreadable. Current readiness and new dependent actions re-evaluate required live premises. Exact retry returns the original event without appending but must include today's readiness overlay, not return an old `ready=True` summary.

Give each fact explicit freshness semantics. Historical occurrence facts can remain true after a normal later event; current assertions such as consent, accepted package, checked issued file, effective payment and current profile must be re-evaluated. Do not require every historical event to equal the latest row, and do not treat every old true value as permanently current. Retained prerequisites remain attached to the workflow until a deliberately modeled phase boundary releases them; later edges must not silently forget consent/package invalidation merely because their local catalog `requires` list is shorter.

## Concrete required failures and acceptance checks

1. Absent/malformed/expired/future policy, wrong operator/catalog/edge/focus, browser-supplied policy, flag-as-stage, unsupported exception edge and arbitrary advanced initialization: no event/evidence/dependency writes. A valid policy for one edge cannot enable another with the same from/to but a different condition branch.
2. V18→V19 and W13→W12 reject the original submission preceding the return-for-revision. Require a new submitted event later than that return in the **same attempt**. Normal later approval must not erase the historical fact that submission occurred.
3. Consent withdrawal, package receipt replacement, passport/fact change, approval revocation, source/policy expiry, or global quarantine after form rendering: new dependent transitions fail and effective readiness becomes unavailable. Stored stage/source facts remain unchanged. Exact retries/historical/read views must not show old current readiness.
4. W18→W19 cannot use a permit's `approved` decision as the resident decision. W19→W20 cannot use a registration belonging to another case/person or an unrelated attempt. U's registration branch cannot reach L-issued stages; a registration application must never change procedure to `exit_visa`.
5. Changing the active application, dependency role or chosen edge in a signed form fails. An approved sibling/spouse/employee cannot satisfy the subject's prerequisite. Refused/closed/superseded linked attempts do not become valid by choosing an old successful-looking event.
6. Terminal application decisions remain terminal in the application journal. Do **not** blanket-block later stage bookkeeping solely because the root application is `approved`: post-issue review/delivery and W15/dependent work legitimately follow approval. Refusal/closed workflow continuation needs the explicitly modeled successor/exception, not reopening the old attempt.
7. Supplied all-true/false strings, numeric booleans, unknown enum values, duplicate facts/pins/roles, future dates, backdated reordering, rehashed wrong source version, and mismatched source scope must fail. Manual attestation cannot replace an authoritative fact just because that source is absent, expired, damaged or rejects the request.
8. Old payment followed by void/correction/refund cannot retain paid readiness. A positive row is not automatically full payment or evidence allocated to every applicant. Payer profile/StayHistory never substitutes for an individual profile/travel fact.
9. Stage request must use the same session for all evidence validation and append. Reuse owned transaction retry; lock the case first, then involved application IDs in deterministic order, with applicant locking as required by profile writers. Do not call public readers that start separate transactions while assembling evidence. Test a source change racing a stage change, dependency swaps, same/different request keys, stale CAS, and before/after-commit loss. PostgreSQL behavior remains UNKNOWN without runtime evidence.
10. Stage/history/evidence bytes, rows, dependency count and manual fields are bounded; integrity replay includes evidence semantics and parent binding, not just matching hashes. Reserve a way to record corrections/withdrawal or fail safe when history is full. Readiness never falls back to PASS after a limit or integrity error.
11. Additive schema, actual SQLite FK/model parity, safe empty cycle, populated/offline downgrade refusal and PG DDL; preserve existing application/package/issued/deadline histories. No portal/payment/message integrations, live settings, real personal data or migration are exercised.
12. Native disabled/unknown/stale states, signed scope, OFF/workday/write gates, historical read/print, mobile and no-JavaScript scenarios. UI must distinguish recorded procedural stage from current readiness and from official application status; no wording claims automatic submission, payment, approval or travel permission.
