## Reviewer F3 / P1 - accepted write can make prior receipts unreadable

Independently reproduced on unchanged r1 with both SQLite and actual PostgreSQL. `_history` compares escaped SQL JSON text length with a canonical UTF-8 budget, whereas `save_draft` charges only canonical UTF-8. A large valid A07 record is approximately 30.5 KiB canonical but 81.4 KiB SQL JSON text. With the history budget scaled between the two two-record totals, the second write succeeds; the next read and exact retry fail `notification_history_limit`. The auditor's probe explicitly accepts either a controlled clean refusal or a readable successful write, so this is not a test demanding one arbitrary quota representation.

Own unchanged probe `runs/auditor-e616-r1/auditor_notification_capacity_probe.py::test_an_accepted_unicode_write_cannot_make_prior_receipts_unreadable`: SQLite 1 FAIL / 8.51 s, `runs/auditor-e616-r1/runs/auditor-capacity-r1.xml`. Its actual-PG wrapper `auditor_notification_pg_probes.py::test_encoded_capacity_preserves_receipts`: 1 FAIL / 13.10 s, `runs/auditor-e616-r1/runs/auditor-own-pg-r1.xml`. The separate reviewer additionally reports the default 4 MiB constants fail after 52 accepted SQLite records; that is reviewer evidence, not an auditor-authored default-limit execution.

Proposed fix assessment: a distinct conservative bound on SQL serialized text materialization, followed by unchanged exact canonical row/history limits, is sound. A factor of six accommodates the standard JSON encoder's ASCII escapes and separators. SQL `length(text)` is a character count rather than a physical UTF-8 byte measurement; the corrected contract must keep that distinction explicit. Final frozen implementation and unchanged own SQLite/PG retests remain pending.
