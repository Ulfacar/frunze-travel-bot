## Conclusion

The smallest defensible bridge is an **explicitly enabled, separately delegated internal review reminder**, initially only for the current helper's UZ ordinary/single-citizenship `work_hire` case. Its date means “review this conditional calculation,” not “official filing deadline confirmed,” eligibility, permission to work/remain, filing, client delivery or automatic process transition. The helper must retain `requires_specialist=True` and `operational_action_allowed=False`. A separate task authority grants only this narrower CRM action; it must not reinterpret those fields as legal permission.

Reuse CalendarTask lifecycle and established binding/recovery behavior, but introduce a distinct versioned calculation receipt/binding contract. Do not inject the computed date into legacy `manual` evidence, silently broaden the original deadline schema, or create a task after a separate unlocked helper transaction. A review reminder can close a genuine calculated-date→internal-task link once implemented and tested; the current standalone helper does not close it, and the one capability does not implement all source deadline families.

## Source meanings and anchors

Original PDF SHA256 `141b9e1e570c916aab65f3dc40e927cc61ef182e1d155b997a5123091e36cca2`; inspected physical pages 82–84, §19.9–19.12, plus Б.8. `runs/e630c-pre-audit/source-pages.txt` retains the prior exact PDF/archive extraction. All **22** retained deadline units still have `value=null`; source clauses and a separately approved interpretation must remain distinguishable.

| Source case | Exact source relation | Required actual anchor / limit |
|---|---|---|
| §19.11 visa extension | **−5 working days** | Current own visa end, with current basis, previous issuer, purpose and in-country type applicability reviewed; TS/TR/R are excluded by this source branch. Not approval date, planned exit, or an unrelated lawful-stay end. `KG.DL.VISA_EXTENSION`. |
| §19.11 and Б.8 visa-free worker → EP | **−10 working days** | Attested actual visa-free permission end. Current `work_deadlines` implements only this conditional UZ capability: `KG.DL.EP_BEFORE_VISA_FREE_END`. Actual entry supports current presence but is not the subtraction anchor. |
| §19.9 W14/W16 and §19.11 EP → resident card | Start preparation **−15 working days**, filing deadline **−10 working days** | Actual own EP end; preparation and filing are separate task purposes. `KG.DL.RC_BEFORE_EP_END` does not make an approval event date equal the EP end. |
| §19.9 W21 and §19.11 new EP | **−7 working days** | Actual own resident-card end. `KG.DL.EP_BEFORE_RC_END`; neither EP end nor visa-free end can substitute. |
| §19.10 EAEU employee | Renewal reminder **−10 working days** | End of the actual 60-day registration pending tax confirmation; registration/continuation service, no EP. Up-to-one-year result remains conditional on tax confirmation, not automatic from the reminder. |
| §19.11 after issue; §19.12 registration | Renew no later than last day; payment **within 3 working days**; re-register **10 working days after** address/passport/purpose change | Different anchors: current registration end, actual payment-code event, actual relevant change. No generic “minus ten” adapter. §19.12 also separately treats absence abroad for 30+ days. |

§19.9 dismissal's ≤3 calendar-day notification and ≤30-day departure observations are another capability; neither is a working-day filing reminder. Source §19.11's urgent tariff/exit-plan fallback does not authorize a tariff choice, automatic exit advice or continued stay while a case is pending.

“Before” does not settle every endpoint/holiday interpretation. Reuse `app.knowledge.deadlines._calculate` with explicitly pinned `count_anchor_day`, `boundary_inclusive`, calendar contents/years/validity and trace. Keep `shift_from_nonworking` explicit. The current-stay margin check only decides a threshold; it is not an exact −5/−7/−10 calculator. Approval must cover every scanned calendar date, including excluded anchors and year boundaries.

## Existing reusable pieces and actual gaps

* `entry_deadline_sources.ANCHOR` accepts only application-event or issued-travel records. `actual_anchor` verifies ownership, source and supersession. It does not expose an actual visa/EP/RES validity end. Its `manual` action expressly requires `portal|official_document`, an evidence date and proof. `summary.operational_due_on` comes **only** from that manual evidence; a draft calculation remains `candidate_due`.
* `entry_deadline_tasks._desired` reads this old immutable deadline journal. Its composite FK binds a task to an actual `EntryDeadlineRevision`; a helper result cannot be placed there without a new compatible contract. Reuse its bounded generations, source/owner token, transaction rollback, exact action receipts, capacity-reserved terminal action, explicit restore, claimed-task refusal and no-reopen rules as behavior—not by mislabeling the new receipt as old evidence.
* Existing `sync_enabled` hooks run atomically for deadline writes, application events and issued travel. They do not cover profile/history/interview updates or source/policy/calendar revocation. Existing resumable case sweep is an operator operation, not a scheduler or authority source.
* `work_deadlines.evaluate` already checks source, exact current person/profile/history/interview, factual authority, calendar and current stops. It is currently an **engine wrapper only**. Extract a semantically identical same-session reader for composition; preserve external behavior and historical fingerprints where applicable. Do not compute first and write a task later.
* `entry_issued_rules` retains a boolean validity check, not structured actual validity dates. The newer process `resident_registration_basis_reviewed` has reviewed RES/registration periods and exact approval pins, but its existing contract is post-RES registration readiness. It is not a generic visa/EP/end-date authority. New supported anchors need explicit own-record provenance and interpretation; do not infer missing dates from these helpers.

## Minimal compatible authority and journal contract

1. Default-empty server authority explicitly scopes `conditional_ep_filing_date_review`, source clause/interpretation, WorkDeadlinePolicy/current-stay/qualification/publication policy digests, operator set, dates and evidence reference. Client POST cannot supply or approve that authority. A receipt pins its full authority document; latest authority is required for a new enable/refresh, while retained authority permits bounded withdrawal/closure after expiry without creating a fresh reminder.
2. Bind exact case, applicant, appropriate own application/procedure and opaque passport continuity; never derive the person from payer/contact. CalendarTask.contact_id may remain the case contact for CRM compatibility, but the authoritative binding must retain the applicant and application. Display that identity without putting raw passport/history/proof data in task text.
3. Store a bounded immutable command/result receipt with actor-bound request key, expected revision, prior hash, exact input/source/policy/calendar/current-evidence pins, calculation trace, due date, checked-at and runtime identity. Add database scope/uniqueness protections. A mutable CalendarTask comment or an unvalidated helper hash alone is insufficient.
4. Under one transaction take the established case→person→publication dependency locks, plus required application/track locks in a consistent order and task lock last. Check any interaction with old case→application→task writers; do not invent a reverse order. Sample current time only after evidence locks. Recompute current evidence, validate expected token, then append receipt, bind/create/change task and append CalendarTaskEvent atomically. A storage failure leaves neither side partially committed.
5. Exact retry returns the retained receipt without recomputation, backfill, task recreation or reopening, including after a later stop/policy expiry/day change. A changed payload or actor under the same key conflicts. Current status is a separate view. Fingerprint changes may refuse replay while preserving verified historical read/retry; do not rewrite historical receipts to new semantics.
6. Avoid making every new `checked_at` or daily `as_of` a new task generation. Same scope/anchor/meaning/date plus refreshed evidence should not reopen completed/cancelled work or duplicate an existing review task. Explicit later re-enablement after a meaningful change needs a new authorized command. Bound receipts/generations/bytes while reserving withdrawal/cancellation capacity.

## Revocation, freshness and existing calendar behavior

CurrentStayFact and the latest profile are explicitly same-day. A future task is therefore **a historical, conditional review reminder**, not a guarantee that tomorrow's filing authority remains valid. Persist the original calculation and show checked-at/currentness separately. Every fresh task action or refresh must assess latest identity/history/interview/purpose/consent, actual anchor, source publication, policy/calendar and clock; an old positive receipt cannot bypass these checks.

Known stale, withdrawn or scope-conflicting evidence must invalidate the action view and reconcile/cancel an unclaimed active projection. Reconciliation requires explicit hooks or a documented bounded operator sweep; a historical snapshot by itself cannot promise prompt cancellation on unrelated mutations. If the bounded first version is operator-reconciled, state that limitation in the UI and acceptance. Retain a reviewable stale marker; do not silently claim automatic revocation. Missing/unknown anchor or authority yields no calculated date, no invented official proof and no fallback date “today.” A known STOP12 result may support an explicitly authorized specialist-review reminder with the stop visible, never a normal filing instruction.

Preserve claimed-task unknown-outcome handling, external manual schedule conflicts, explicit current-token restore, owner changes and terminal history. New revocation must not silently erase or reschedule claimed work. `app.admin.router._calendar_task_for_action` currently recognizes **only EntryDeadlineTask** for the bound claimed-task refusal: a separate binding must be covered by this existing guard and both native calendar writers, or it loses that protection.

Use a date-only task (`scheduled_at=None`) and no channel `user_id`: `task_rules.due_tasks` excludes such tasks. However, `CalendarTaskService.today_for_manager` includes them in `calendar_brief`, which may send the comment to the manager under its existing default-off feature flag. Therefore “the adapter makes no provider/client call” is accurate; “this row can never produce any downstream notification” is not. Preserve the existing delivery gate, put only safe internal review wording in the comment, and test the actual summary path. A strict screen-only requirement would need an explicit exclusion. Do not copy the old task's “confirmed date” wording for a conditional calculation.

## Acceptance and negative controls before approval

* Connected positive: same current UZ person/history/interview → separately authorized exact −10 calculation → explicit confirmation → one dated internal task with receipt and existing calendar visibility; same-person source provenance is inspectable; no filing/transition/payment/message or eligibility mutation.
* Independently check both delegated endpoint modes, holidays/working Saturday, crossed years/missing calendar, due-day equality and the distinction between ten exact working days and threshold-only current-stay headroom.
* Wrong person/application/passport, competing purpose, changed interview after acknowledgement, withdrawn consent/history, unknown actual end, absent/expired policy, changed source/calendar/clause and null source value without the separate delegation all refuse fresh date/task creation. Keep triggered specialist stops visible.
* Concurrent duplicate/CAS, withdrawal while enable waits, midnight after lock wait, failure between receipt/task/event, lost commit acknowledgement, original retry after withdrawal and runtime change: verify exact-once projection and durable history with real PostgreSQL when the implementation exists.
* Owner absent/change, generic-calendar manual reschedule/claim, corrupted same-case pointers/typed receipt identities, capacity and cancel-at-capacity; no resurrection after completion/cancellation, no new generation merely from daily revalidation.
* Native explicit prepare/confirm, signed full operation/person/pins, CSRF/access/pilot gates, 409/422 and controlled 503 retaining the original request; historical/current separation, no raw proof entry masquerading as approval. Verify calendar text/links and truthful “conditional review” labels.
* Keep old official-manual deadline histories, retries, legacy native tasks and populated migration behavior unchanged. Existing E6-19 tests are relevant regression controls, not evidence for the new source path until rerun against its actual implementation.

No new business decision is necessary to build this **inactive synthetic local capability**. Real source/calendar/endpoint interpretation, authorized operators and activation still require their existing owner gates. Broader −5/−7/other −10 capabilities each need their own factual anchor/applicability/authority; they cannot be awarded by expanding an enum or reusing the UZ helper's positive result.
