## Confirmed finding in r2

**P2 / FAIL — an unchanged affirmative consent answer creates a false permanent withdrawal.**

Normal domain sequence: start → explicitly answer `consent.given=True` → record valid consent date/reference/SHA → verify `consent_complete=True` → explicitly save `consent.given=True` again. `rules.apply_answers` assigns a new revision even though the current fresh canonical value is unchanged. The three consent proof fields then have stale parent contexts. `_reduce_v1` treats loss of completed consent as a withdrawal, records `consent_withdrawal={revision:4,actor:admin,on:2026-10-11}`, sets permanent collection blocking and creates a handoff. No consent was withdrawn or removed. The UI's explicit correction flow can submit this command, and the one-interview-per-applicant rule prevents restarting around the block.

Independent probe: `runs/auditor-e612-r2/runs/auditor_interview_semantics.py::test_affirmative_same_consent_does_not_record_withdrawal`, executed with the real synthetic SQLite domain fixture and normal service calls, no database forgery. Command from that execution copy:
