## Findings

### P1 — JSON-поля мигрируются как INTEGER

Начальная версия `alembic/versions/e6_process_journal_0027.py:24` создавала `command`, `snapshot`, `policy`, `evidence` через `sa.Integer()`, тогда как модель использует `_ServiceJSON`.

Триггер: запись первого события после миграции PostgreSQL. Типы JSON-параметров ORM несовместимы с integer-колонками. SQLite может хранить текст в такой колонке и скрывать проблему при обычной вставке.

Доказательство: непосредственно прочитанный код миграции и модели. PostgreSQL runtime не запускался. Исправление: JSON по соглашению соседних миграций, parity по типам и явная проверка PostgreSQL DDL. Автор сообщил об исправлении; позднее чтение архива подтвердило `sa.JSON()` для всех четырёх колонок. Независимый миграционный ретест исправления пока **UNKNOWN**.

### P1 — этап можно датировать раньше собственного доказательства

Места исходной версии: `entry_process_evidence.py:130` выбирает источники относительно времени записи; `:190` проверяет статус согласия, не его дату относительно этапа. `entry_processes._evidence` получает время записи, а `entry_process_rules.apply` сравнивает `operation.on` лишь с предыдущим `state.on`.

Независимое воспроизведение через штатные domain API:

1. Создать registration workflow с датой `2026-08-01`.
2. Сохранить индивидуальную анкету с `as_of=2026-10-09`, подтвердить её полноту датой `2026-08-01` и выполнить R01→R02 с той же датой. Получено `stage=R02, on=2026-08-01`.
3. В комплекте REG записать согласие с датой `2026-09-03`; подтвердить основание пребывания датой `2026-08-01`.
4. Выполнить R02→R03 с датой `2026-08-02`. Получено `stage=R03, on=2026-08-02`, хотя обязательное согласие датировано месяцем позже.

Следствие: журнал удостоверяет этап до появления его обязательного основания. Синтетическая база: `runs/e6-10-local/runs/reviewer-process-preliminary2/domain.db`.

Автор выбрал исправление: initialize/link/transition фиксируются текущим днём записи, исторический backfill этапов пока не поддерживается; profile-bound attestation не может предшествовать созданию выбранной версии анкеты. Независимый ретест этой новой семантики пока **UNKNOWN**.

### P2 — закрытая попытка сохраняет общую ready=true

Место исходной версии: `entry_processes._readiness`, около строк176–195. Общая готовность вычисляется из retained-фактов и политики без проверки текущей активной попытки.

Независимое воспроизведение: initialize V01, затем штатный `record_application_event(status='closed', source='client_request', reference=None)`. `read_process_history` вернул:

```json
{"ready":true,"reason":"current_evidence","retained":{}}
```

При этом единственный переход вернул `ready=false, reason=process_application_terminal`. Следствие: текущая сводка и возвращаемая при exact retry готовность могут положительно описывать закрытую попытку. Новое продвижение этим сценарием не разрешилось.

Та же синтетическая база. Исправление: проверять usable активной попытки при общей current readiness, сохранив возможность явных корректирующих/завершающих операций. Автор сообщил об исправлении; независимый ретест пока **UNKNOWN**.

### P1 — время создания не восстанавливает историческую видимость транзакций

Места исходной версии: `entry_process_evidence.py:130–131`, `:152–159`; повторный расчёт в `entry_processes._history`.

Сценарий гонки по коду: загрузка карантина в другом case получает `created_at` раньше процессного события, но остаётся незакоммиченной. Процессная транзакция не видит receipt и записывает положительное основание. После commit загрузки повторная историческая проверка заново обнаруживает receipt с `created_at <= process.created_at` и меняет сохранённое evidence, вызывая `process_evidence_changed`. Исторический факт становится нечитаемым вместо сохранения истории и блокировки только текущей готовности.

Аналогичный риск существует для денежной строки, которой ORM назначает timestamp до ожидания FK/case lock: поздно видимая строка может попасть в старый временной префикс. Сохранённые типизированные source pins пока не используются как границы исторического resolver.

Это статический finding о границе видимости; конкурентное воспроизведение на PostgreSQL **UNKNOWN**, не заявляется как выполненный тест. Автор согласился с причиной и меняет replay на явно наблюдавшиеся source IDs/границы, включая историческое отрицательное наблюдение карантина. Текущая readiness должна продолжать live-проверку. Автор также планирует общий транзакционный lock перед case lock у process/upload writers. Новый дизайн ещё не проверен этим рецензентом.
