### Минимальная схема без новой интеграционной платформы

Достаточно двух новых immutable сущностей и существующего application writer:

1. **Receipt**: identity/case; kind `email_observation` либо `manual_observation`; source channel и opaque source namespace; transport key либо manual request key; original input SHA256/UTF-8 byte count; parse version; immutable policy snapshot/hash; bounded structured reference/kind candidates; received timestamp; untrusted reported date, если она извлечена; минимальный archive reference/proof; actor/time/request hash/snapshot hash. Receipt не хранит mutable status и не имеет authoritative application event.
2. **ReceiptAction**: receipt/case; consecutive revision и previous action; action `correlate`, `dismiss`, `confirm` (при необходимости отдельный `duplicate`); immutable typed command/result/evidence; actor/time/request hash/snapshot hash. Correlation pin: application/case/applicant/procedure, reference, exact claim-bearing event и submission-cycle event IDs/hashes. Confirmation pin: expected head ID/hash/revision, verified date/source/proof, result application event ID/hash. Не допускать silent rebind уже применённого receipt.

Scope обеспечивается составными FK, а применение подтверждения — уникальной связью receipt → applied event и semantic replay. Если подход требует дополнительного narrow dedup claim, он должен сохранять эту же атомарность; общая очередь или почтовый сервис здесь не нужны. Формулировки disposition и лимиты нужно закрепить в rules/test, а не оставлять непроверенным JSON.

**Claim и provenance — разные вещи.** SHA256 защищает воспроизводимость сохранённой записи, но не доказывает отправителя или достоверность содержания. Ручная независимая проверка — зафиксированное утверждение авторизованного оператора, а не криптографическая верификация портала. UI должен говорить это обычным языком.

### Минимальный протокол подтверждения

1. Авторизовать именованного full-admin, bounded command и explicit confirmation; никаких system/bot actors. Прочитать receipt и проверить сохранённые хеши, типы и scope.
2. В owned transaction взять case write lock, затем нужный application write lock; далее receipt/action lock или сериализацию через уже взятый case lock. Не брать receipt first, если другие writers используют case first. SQLite должен физически начать транзакцию как существующий `_run`.
3. Найти exact request retry, проверить content и ранее связанную историю. При совпадении вернуть первоначальный результат до current policy/CAS. Никакой новой synchronization на таком replay не требуется.
4. Для новой команды проверить explicit live authority, receipt disposition/correlation, exact head CAS и submission cycle. Отдельно проверить фактическую verified date не из arrival timestamp. Ошибка не обязана создавать action в той же откатываемой транзакции: само pending observation уже сохраняет вход; при необходимости оператор делает отдельный dismissal.
5. Вызвать session helper существующего event writer со строго разрешённым status и source, при этом сохранить `_event_facts`, reference constraints, request hashing и `sync_enabled`. В helper не должен появиться самостоятельный commit, новая engine session или swallowing exception.
6. После получения event ID записать action и его event pin. Любой insert/flush/task error откатывает event, reference claim (если такой путь предусмотрен), task changes и action. При lost ACK возвращается UNKNOWN, native UI сохраняет тот же signed envelope для exact retry, даже если повторное чтение страницы также недоступно.
