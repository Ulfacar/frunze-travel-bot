## Recommended completion boundary

Proceed with a bounded **operator-selected internal review**, connected to the current own process/application/person and a closed source duty. Reuse `EntryDeadlineRevision` / `EntryDeadlineTask` through a distinct versioned format. Keep the existing official-manual and conditional-calculation meanings intact. No parallel task journal, automatic SLA engine, external message, automatic stage escalation, payment or legal deadline is needed.

Fixed J01 is “End-to-end source SOP scenarios exercise actual connected functions.” It does not require automatically computing every SLA cell. A real source-scoped task, intentionally scheduled by an operator and shown in the workday/calendar, is meaningful connected implementation for a manual source duty. It must be labeled **operator-selected**, retain its evidence and survive/reject the right recovery cases. A generic contact task with a source phrase in its comment or `followup_completed=True` does not provide the needed own-person/process boundary.

Missing annual, quarterly, exemption or ban timing is a reason to schedule **verification/review**, not permission to invent its expiry. For example, “review this student's actual REG/RES documents” at a chosen time is valid; “registration legally expires on this date” is not established by choosing a task date. Source-derived calculations remain in the separately reviewed D/UZ capabilities. Default real E authority stays empty, and real activation/owner acceptance remains J05.

## Actual inspected reuse points and risks

Read actual `entry_deadlines.py`, `entry_deadline_sources.py`, `entry_deadline_tasks.py`, `calendar_tasks.py`, `task_rules.py`, `entry_processes.py`, `entry_process_rules.py`, relevant models, process catalog/preview, general native task routes and the C connected tests before the E task's conclusions. Stable C revision is `ca789334af33ce6c42bdb6dfbeb4955d7e870ce9`; D is an independent uncommitted component. Read-only identities and verified C artifacts are in `runs/e630c-source-acceptance-review/j01-r45-evidence.json`. D R17 source mapping is explicitly separate from changing root bytes; no E code is approved by this pre-audit.

1. **Official manual is not generic manual.** Legacy `entry_deadline_sources.MANUAL` requires `portal`/`official_document` evidence and means an official date. Its summary is the only legacy operational date. Add an independently identified E operation/format; do not write an operator-selected time into that path or coerce it into D's conditional arithmetic.
2. **The journal already has the required ownership spine.** `EntryDeadlineRevision` has per-application/rule revision and request uniqueness, a same-scope previous link, immutable command/snapshot and a 250-row/4MiB bounded stream with one terminal clear. Its old application/travel FK columns cannot be abused as process/profile pins. A small relational evidence pin, with same-case/person/application constraints, is justified; a second operation journal is not.
3. **A process stage string is insufficient evidence.** `entry_processes._history` validates immutable events and pins; `_policy` / `_authorize_operation` enforce the retained/current process authority. Current process state has a root and potentially distinct active linked applications. Pin the exact root process and applicable linked application/role; do not select the newest process merely by shared contact. `EntryProcessEvent.created_at` is recording time, and `operation.data.on` is only a date: neither establishes the exact time an external invoice/email/document was sent.
4. **All current task checks assume date-only.** `_view`, `_reconcile`, action checks and `deadline_bound` audit compare the expected date and treat any non-null task timestamp as a conflict. `_desired` hashes only date/owner/source. A time field added only to task creation would be inconsistent and could miss same-day tampering. See the migration/time contract below.
5. **Exact-time tasks enter a different existing queue.** `task_rules.due_tasks` includes only non-null `scheduled_at`; `claim_task` itself checks active/unclaimed state, not current source policy. Adding exact times makes E rows eligible where D date-only rows were not. Inspect actual consumers, retain empty client `user_id` and internal action meaning, and do not turn them into outbound jobs. Existing claim protection must remain intact during reconcile/clear.
6. **General native creation is too broad for this claim.** `/conversation/{user_id}/task/create` and `/calendar/task/create` resolve contact/conversation and create a generic task; they do not retain the source application/person/process head. Reuse the calendar UI/lifecycle, but expose a scoped E operation from the own application/process. A test that creates a generic task then manually attaches missing scope is a test-only bridge, not product acceptance.
7. **Historical truth and current relevance are different.** A later process change must make an old duty non-current without corrupting the original receipt or preventing retained cancellation. Config/source expiry cannot magically mutate a stored task. Current views/pre-action validation and explicit reconcile must honestly indicate that boundary; source-write hooks can cancel eligible projections atomically where supported.

## Command, evidence and authority contract

* New E format with strict canonical schema; exact IDs/booleans, known source duty, explicit confirmation, bounded text, selected local date and optional `HH:MM` or a single canonical equivalent. Retain the actual chosen date/time and selection origin. A null exact time means date-only; never silently choose midnight.
* Command binds case, own applicant, root process application, current active/source application role as applicable, process head ID/hash, current own profile and application-event IDs/hashes, expected E revision/request key, actor and expected E authority digest. Current same-subject material interview/privacy stop checks must also be respected. A shared payer/contact or employer never substitutes for the applicant.
* Relational pin ties the E receipt to the actual own immutable process/profile/application evidence. Use composite scope/FKs where available and strict semantic verification where a relation is conditional. It may be a compact evidence row or additive typed nullable references, but cannot be a loose unvalidated JSON ID. Do not populate legacy `anchor_event_id` with a process ID simply because both are integers.
* Default-empty immutable E authority binds original source hash, exact closed duty catalog/definition and process catalog digests, applicable stages/actions, explicit operators, validity/review bounds and the supported source/review/publication contract. It confers internal scheduling only. The policy must not approve law, source values, eligibility, consent, fees or sending. Exact current source dependencies must be declared; arbitrary “at least one approved unit” is insufficient proof of the selected duty.
* Verify current process/profile/application/own-person consistency and current source authority in the transaction used to write receipt/task. Do not treat a preserved process catalog or an old signed process receipt as current E delegation. Reuse current own-source/collection-stop readers; sensitive-profile collection being blocked cannot be bypassed by calling the new page.
* Historical verification independently checks the original immutable evidence prefix, original policy/duty semantics and canonical schedule at recording time. Rehashing a receipt cannot authorize a different process, person, actor, stage or time. Current unrelated successor rows must not retroactively invalidate a genuine retained receipt. Original receipt/retry remains readable when current authority/source changes; current relevance is a separate result.
* Fresh commands require current authority. Retained clear/cancel after authority loss uses the same narrowly retained operator authority/access contract, and cannot create/update a schedule. Terminal reserve must not admit another ordinary command. No automatic backfill of missing evidence, contact inference or receipt reconstruction.

## Exact-time migration and task integration

Adding nullable `EntryDeadlineTask.expected_at` via additive migration0043 is reasonable. Old rows stay `NULL`, preserving the old rule that any task timestamp is a manual schedule conflict. Do not backfill from current `CalendarTask.scheduled_at`, which could already be an unauthorized/manual change.

Canonicalize supported Bishkek wall time to one exact UTC instant; verify `scheduled_date` equals that instant's Bishkek date. Reject malformed/noncanonical values, naive ambiguous instants, offset inconsistencies, seconds if not supported, booleans/coercions and same-day different-time tampering. SQLite may reload timezone-naive datetime values; compare their canonical stored UTC meaning deliberately, matching existing `applications._utc`, without accepting a naive caller timestamp as an unspecified timezone.

Carry selected time through desired/source/target hashes, native signed preview, token, task create/reschedule, binding expected state, `deadline_bound` after-state audit, current view, complete/cancel/escalate conflict checks, recovery and receipt display. Preserve every date-only path. A historical bound-event proof must match E receipt, case/person/application, task ID, actor and schedule; comparing only its date is insufficient for E. Historical receipt verification must not depend on the mutable task still having that time today.

Use the existing owned `CalendarTask` and task audit, with empty client `user_id`, internal follow-up kind and comment identifying **operator-selected review**. Do not set official/conditional/permission fields to the chosen time; no `operational_due_on` reuse that changes its meaning. Machine-claim/due-task behavior must be explicitly examined because exact-time rows enter `due_tasks`. Claimed tasks remain an attention/conflict state; do not clear a claim, cancel/reassign claimed work silently or mark client delivery.

An explicit schedule revision may reschedule one eligible active binding atomically. A completed/cancelled task must not reopen on read, original retry, owner change or authority return. A genuinely new review requires an explicit new accepted source operation and current authority, respecting generation bounds. Unrelated source/head changes may conservatively make E stale; a refresh must not silently revive its old selected time under a new profile or stage.

Use existing case/application/task lock order and source locks. Process/profile/application writers and E writes share the case lock; lock linked applications deterministically. Sample time after required lock waits, reject future evidence/head/clock reversal, and validate the final source head used for the receipt. Receipt/pin/task/audit writes must commit atomically. Because a write may be rolled back at outer scope, do not swallow failures and commit a half-created task.

Relevant source-write hooks can reconcile enabled E tasks in their transaction. Source/config expiration without a write is not automatic cancellation: current read/pre-action checks show stale, explicit refresh cancels only an eligible unclaimed task, and a bounded sweep can be reused. No automatic scheduler deployment is part of this slice.
