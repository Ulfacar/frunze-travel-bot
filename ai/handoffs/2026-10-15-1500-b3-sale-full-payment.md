## Что сделано

Правило: `paid − refunded ≥ agreed` в валюте договора, сумма известна, нет сломанных строк;
`unconverted` не считается (`service_money.is_fully_paid`). Продажа в домене — событие
`service_events.sale_full_payment`, один раз на дело (не `ServiceCase.outcome`: он означает «дело
закрыто», а после оплаты услуга ещё исполняется). Диалог(и) клиента в направлении дела →
`claim_outcome(user_id, "won")` (атомарная защёлка, финал не перезатирается) + `sale_amount` =
сумма договора. Журнал панели: ровно один `sale_full_payment` на дело (его считает
`scripts/pilot_daily_summary.py`), по диалогам `sale_fp_dialog` / `sale_fp_conflict`, возврат после
продажи — `sale_fp_reversal` (домен: `sale_reversal_flag`, обратно — `sale_restored_flag`).
Bitrix новый писатель не трогает. Срабатывает после **любой** денежной операции в карточке услуги
(`workday._write` → `after_commit`), сбой шага не ломает ответ об оплате; повтор дозакрывает.

Флаги (оба OFF, env + `FEATURE_FLAGS` + `docker-compose.yml`):
- `sale_by_full_payment_enabled` — вывод продажи из баланса.
- `sale_check_panel_contract_enabled` — вечерняя ссылка «Оплатил»: без CONVERTED в Bitrix, ссылка на
  договор в панели, тексты без Битрикса. Ответ менеджера и `sale_check_won` в журнале сохраняются.

Файлы (границы объявлены в плане; сверх плана — два, объяснены):

## Непроверенное и открытое

- **Долг из аудита р.3 (LOW, кодом не закрыто):** L1 — `sale_fp_conflict` пишется без `user_id` в detail,
  при прямой правке БД (`lost` → нефинал) лечение поставит `won`; L2 — сбой на записи `sale_fp_dialog`
  после защёлки оставляет `won` без строки в журнале; L3 — `audit_exists` ищет префиксом LIKE без
  экранирования `_`/`%` (на PG `_` — подстановка; только в безопасную сторону — пропуск лечения);
  L4 — если на момент продажи диалога не было (`no_dialog`), появившийся позже `won` автоматически не
  получит. Производительность `audit_exists` на боевом `audit_log` (нет индекса на `detail`) не мерилась.
- **Из аудита р.1, MEDIUM, не закрыто кодом:** (а) если проверка продажи упала на последней оплате
  (`error`), повтора не будет до следующей денежной операции — досчёта по таймеру нет; (б) при
  включении флага уже полностью оплаченные дела задним числом не пересчитываются. Долг: разовый
  скрипт/кнопка «пересчитать продажи по делам» — по решению Алана.
- Откат по данным необратим: `claim_outcome` затирает рабочий авто-статус (`in_progress`/`office`/
  `manager`), прежнее значение не сохраняется. Флаги OFF останавливают новые записи.
- Под блокировкой дела выполняется скан `all_conversations_light()` (тысячи строк) и берётся второе
  соединение из пула; под нагрузкой возможен `error` (оплата при этом сохранена). Дела направления
  `tickets` диалог не находят (`no_dialog`).
- **NEEDS_HUMAN_DECISION (из ревью р.2, S8):** под `sale_check_panel_contract_enabled` тап менеджера по
  вечерней ссылке по-прежнему ставит `won` без полной оплаты (отключена только запись в Bitrix).
  Если «продажа = только полная оплата» должна быть строгой, ссылка тоже не должна ставить `won`
  (а только вести к договору). Сейчас — по ТЗ S8 как написано.
- `won` ставится всем диалогам клиента в направлении дела, включая старые без финала — отчёты по
  диалогам могут посчитать одну продажу несколько раз (запись `sale_full_payment` при этом одна).
  Политика: один диалог (последний активный) или все — решение Алана.

- Конкурентные POST на PostgreSQL (две оплаты одновременно) — только по коду; тест на PG не писал.
- `sale_amount` = сумма договора (не «названное менеджером»); `bitrix_pipeline._sale_amount` берёт это
  поле в `OPPORTUNITY` сделки под своими флагами — косвенное влияние на Bitrix через старый писатель.
- Два диалога одного направления с одним номером получают `won` оба (по ТЗ «диалог(ов)»). Диалог с
  ручным `lost` — `conflict`, `won` не ставится: по замыслу, но для менеджера выглядит как потеря;
  **NEEDS_HUMAN_DECISION** (низкий приоритет, пока запись в журнале).
- `refund_due` и возвраты в чужой валюте без курса продажу не отменяют (ровно по ТЗ); сигнал —
  `needs_attention` в блоке денег.
- Реальная проверка в браузере карточки услуги с баннером — не делалась (только рендер в тестах).
