## 2. Границы задачи

**Делаем:** детерминированное извлечение фактов из реплики клиента и слияние их в
`qualification` на каждом ходу туровой воронки.

**НЕ делаем:**
- не трогаем промпты — залипание на питании лечится тем, что факты уже собраны, и
  отдельным ТЗ на дисциплину вопросов;
- не добавляем LLM-извлечение: разбор, выразимый правилом, не должен быть моделью
  (закон 1, и наш собственный опыт с бюджетом и датами — `cb7f427`);
- не трогаем визовую воронку и `score_visa`;
- не меняем `search_tours` и его аргументы: когда модель зовёт инструмент, приоритет
  у её аргументов;
- не трогаем конвейер карточек, сигнал «клиент передумал» и стадии.

## 3. Что извлекаем и по каким правилам

Модуль `app/agent/facts.py`:

```python
FIELDS = ("destination", "region", "departure_city", "budget", "dates",
          "tourists", "children_ages")

def extract(text: str) -> dict            # только уверенно найденное, иначе {}
def merge(known: dict, found: dict) -> dict   # пустое НЕ затирает известное
```

Разборщики уже написаны и обкатаны боем — переиспользовать, а не писать заново:
`_parse_dates`, `_parse_tourists`, `_parse_budget`, `_parse_nights`, `_parse_meal`,
`_parse_stars` в `app/integrations/tourvisor/client.py`.

Три правила, из-за которых наивная регулярка не годится:

1. **Маркер обязателен.** Число становится бюджетом только рядом со словом-маркером
   (`бюджет`, `до`, `сом`, `доллар`, `$`, `тыс`) — иначе «457838 Аширбаев» и «3800
   выходит» превратятся в бюджет. Число становится составом только рядом с маркером
   состава (`нас будет`, `взрослых`, `детей`, `человек`, `вдвоём`) — иначе «2 с багажом
   1 ручная» станет двумя туристами.
2. **Прошедшее время — не факт о поездке.** Фраза с маркерами прошлого (`в прошлом году`,
   `вышло`, `было`, `ездили`, `в прошлый раз`) не даёт ни бюджета, ни состава. Боевой
   пример: «У нас в прошлом году на двоих в 5 звезд отель вышло 1200 с завтраком».
3. **Отрицание перед городом.** «Не из Бишкека, а из Алматы» → `departure_city = Алматы`.
   Берётся город ПОСЛЕ противопоставления, а не первый найденный.

Направление и курорт — по закрытым спискам (страны, с которыми мы работаем, и курорты
Турции/ОАЭ/Египта). Города вылета — по списку `FRUNZE_DEPARTURE_CITIES`. Что в списки
не входит, направлением не считается: «>Сеул >Нагоя» из билетного диалога не должно
уехать в туровую карточку.

## 4. Точка врезки

`app/agent/runner.py`, туровая воронка: **после** получения реплики клиента и **до**
вызова модели.

```python
found = facts.extract(user_text)
if found:
    state.qualification = facts.merge(state.qualification, found)
    _sync_qualified_if_ready(state)
```

Почему до модели, а не после: собранные факты должны попасть в контекст того же хода —
тогда бот перестаёт переспрашивать уже названное, и залипание на питании само становится
безобидным (карточка полна независимо от того, дошёл ли бот до поиска).

Почему приоритет у аргументов `search_tours`, а не у нашего разбора: модель видит весь
диалог, разбор — одну реплику. Порядок сохраняется сам собой — `_tours_exec_tool`
отрабатывает позже в том же ходу и перетирает своим.

Голосовые: если расшифровке не доверяет guard (`app/core/stt_guard.py`), извлекать из
неё нельзя — кыргызская каша даёт связный на вид, но выдуманный текст.

## 6. Замер вместо обещания (закон 5)

Тесты проверяют логику, а не калибровку. Поэтому в задачу входит
`scripts/facts_replay.py`: прогон `extract` по РЕАЛЬНЫМ клиентским сообщениям из базы
(`--limit N`, по умолчанию 500 последних туровых) с выводом по каждому полю — сколько
сообщений дали значение и какие именно, чтобы ошибки было видно глазами.

Порог приёмки: на выборке в 100 сообщений, размеченных вручную, **не больше 2 неверных
извлечений** и ни одного неверного бюджета. Бюджет строже остальных: он уезжает в сумму
сделки.
