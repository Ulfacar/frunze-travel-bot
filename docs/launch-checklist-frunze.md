# Launch checklist Frunze Travel

Актуальная схема запуска: домен подключен через Cloudflare, деплой планируется на Coolify, канал WhatsApp через Wappi, два бота на старте - `getvisa` и `frunze_tours`. TourVisor подключается ближе к финалу после оплаты/активации со стороны клиента. LLM - через OpenRouter.

## Что уже есть / подтверждено

- Домен куплен и активирован в Cloudflare.
- Деплой будет через Coolify.
- Wappi есть.
- На старте нужны 2 бота:
  - `getvisa` - визовая воронка, Wappi profile `2f099bc3-478d`;
  - `frunze_tours` - туры, Wappi profile `02a4708d-ec6c` (`FrunzeTravel2`).
- TourVisor подключается в конце, когда клиент оплатит доступ.
- OpenRouter используется как провайдер LLM, оплачивает клиент.
- Доступ к Bitrix24 есть.
- Первый тест делают менеджеры: они пишут ботам от лица клиентов.

## Важные архитектурные решения

### Наша админка и Bitrix24

Продуктовое решение: менеджеры работают с диалогами в нашей админке, потому что там удобнее держать чат, полный контекст, AI-summary и перехват бота. Bitrix24 остается CRM-слоем: сделки, стадии, база клиентов, ответственные и отчеты.

Практичная схема:

- наша админка - рабочее место по диалогам: канбан, чат, полный контекст, перехват, ручной ответ;
- наш backend - AI-движок, хранение полного контекста, правила, интеграции;
- Bitrix24 - CRM-зеркало: сделка, стадия, ответственный, комментарий/summary, история ключевых действий;
- сайт на домене - публичная точка/лендинг/виджет, но не замена CRM.

Главное правило: менеджер не должен прыгать между интерфейсами, чтобы ответить клиенту. Если перехват делаем в нашей админке, то там же должен быть полный чат и отправка ответа клиенту. Bitrix24 получает синхронизированную сделку и summary.

### TourVisor и Bitrix24

TourVisor не нужно считать частью Bitrix24. Это отдельный туристический API/модуль.

Правильная схема для бота:

```text
TourVisor API
     |
наш backend / AI-agent
     |              |
  Bitrix24        сайт
CRM/сделки       публичная часть
```

Если у клиента есть модуль TourVisor для сайта на 1C-Битрикс CMS, это отдельная история и не равно интеграции с Bitrix24 CRM.

Для бота TourVisor должен вызываться нашим backend-сервисом, а результат уже сохраняется в диалог/сделку.

## Что нужно сделать до теста менеджерами

### 1. Coolify / инфраструктура

- Задеплоить приложение на Coolify.
- Подключить домен из Cloudflare к приложению.
- Проверить HTTPS.
- Проверить health endpoint / старт приложения.
- Включить Postgres и Redis в продовом окружении.

### 2. Env-переменные

Обязательные переменные для первого теста:

- `OPENROUTER_API_KEY`
- `OPENROUTER_BASE_URL=https://openrouter.ai/api/v1`
- `LLM_MODEL_MAIN`
- `LLM_MODEL_CHEAP`
- `WAPPI_TOKEN`
- `BOTS`
- `DATABASE_URL`
- `REDIS_URL`
- `STATE_BACKEND=redis`
- `PANEL_BACKEND=postgres`
- `ADMIN_USER`
- `ADMIN_PASSWORD`

Для Bitrix24:

- `CRM_BACKEND=bitrix24` - если сразу тестируем создание/движение сделок;
- `BITRIX24_WEBHOOK_URL`;
- `BITRIX_CATEGORY_BY_FUNNEL`;
- `BITRIX_STAGE_MAP`.

Если Bitrix хотим подключить после теста диалогов, временно можно оставить `CRM_BACKEND=postgres` или `stub`.

### 3. OpenRouter в коде

LLM-слой уже переведен на OpenRouter:

- прямой зависимости от Anthropic SDK больше нет;
- настройки OpenRouter добавлены в `app/config.py`;
- `.env.example` обновлен;
- tool-use сохранен через адаптер OpenRouter -> внутренний формат агента.

Перед реальным AI-тестом осталось вставить `OPENROUTER_API_KEY` в Coolify и проверить один живой запрос к модели.

### 4. Wappi

- Настроить webhook на `https://<domain>/webhook/wappi`.
- Проверить, что Wappi присылает `profile_id`.
- Связать профили с ботами через `BOTS`.
- `WAPPI_TOKEN` не хранить в репозитории; вставлять только в `.env`/Coolify.

Пример целевой структуры:

```json
[
  {
    "id": "frunze_tours",
    "scenario": "tours",
    "title": "FrunzeTravel2",
    "wappi_profile_id": "02a4708d-ec6c"
  },
  {
    "id": "getvisa",
    "scenario": "visa",
    "title": "GetVisa",
    "wappi_profile_id": "2f099bc3-478d"
  }
]
```

### 5. Bitrix24

Нужно получить/зафиксировать:

- адрес портала;
- incoming webhook URL;
- ID воронки туров;
- ID воронки виз;
- ID стадий по каждой воронке;
- кто ответственный менеджер;
- где менеджер перехватывает диалог: в нашей админке или в Bitrix Open Lines.

Для первого теста менеджеров достаточно, чтобы:

- диалог сохранялся полностью;
- карточка появлялась в нашей админке;
- менеджер видел полный контекст и мог перехватить;
- после перехвата бот молчал;
- stage обновлялся хотя бы во внутреннем канбане;
- сделка/summary уходили в Bitrix24, если CRM-интеграция включена на тесте.

### 6. TourVisor

TourVisor не блокирует первый тест, если тестируем квалификацию и передачу менеджеру.

До финального запуска нужно:

- оплатить/активировать XML/API поиск;
- проверить, что search/result больше не дают `Authorisation Error`;
- подключить реальные параметры поиска;
- добавить fallback: если TourVisor недоступен, бот собирает заявку и передает менеджеру.

## Как тестируют менеджеры

Менеджеры пишут ботам как клиенты. Это правильно, потому что они сразу проверят продажи, тон и передачу в работу.

Нужно дать им сценарии:

### Visa

1. Обычный клиент: "Хочу визу в США, раньше виз не было".
2. Рискованный клиент: "Был отказ, документов мало, нужна гарантия".
3. Горячий клиент: "Хочу сегодня записаться, куда приехать?"
4. Нецелевой/сложный: "Сделаете 100% визу без документов?"

Проверяем:

- бот задает правильные вопросы;
- не обещает гарантию;
- дает аккуратную оценку;
- зовет в офис/на созвон;
- создает/двигает карточку;
- менеджер видит полный контекст.

### Tours

1. Обычный клиент: "Хочу тур в Турцию на 7 ночей".
2. Клиент без бюджета: "Подберите что-нибудь хорошее".
3. Нереальный бюджет: "5 звезд all inclusive за очень дешево".
4. Горячий клиент: "Готов оплатить, дайте менеджера".

Проверяем:

- бот собирает город вылета, даты, состав, бюджет, питание, звездность;
- без TourVisor не выдумывает цены;
- честно говорит, что передаст подбор менеджеру;
- горячего клиента быстро передает менеджеру.

## Критерии готовности к первому тесту

Первый тест можно проводить, когда:

- приложение открывается по домену;
- Wappi webhook доставляет входящие сообщения;
- оба бота правильно маршрутизируются по `profile_id`;
- OpenRouter отвечает;
- диалоги сохраняются;
- менеджер видит полный контекст;
- перехват останавливает бота;
- админ-доступ защищен нормальным паролем.

## Критерии готовности к боевому запуску

Боевой запуск возможен после:

- успешного теста менеджерами;
- фиксации стадий Bitrix24;
- настройки ответственных менеджеров;
- правил визовой оценки или хотя бы согласованной категории `высокие / средние / низкие`;
- правил передачи человеку;
- понятного ночного/выходного сценария;
- TourVisor API для реального подбора туров или явного решения запускаться без цен.
