# Эрмеку: доступы и начало работы с Frunze Travel

Подготовлено 08.10.2026 по коду, настройкам проекта и состоянию GitHub.
Это перечень доступов и инструкция для подключения. Выдача учётных записей и
проверка входа Эрмека ещё не выполнены. Координатор передачи — Алан.

На момент проверки репозиторий **публичный**. В этом файле нет паролей, токенов,
приватных SSH-ключей, адресов внутренних подключений и данных клиентов.
Само приглашение в GitHub не предоставляет доступ к серверу, CRM или API сервисов.

## 2. Перечень доступов

Таблица охватывает разработку и сопровождение. Конкретные production-права
Эрмека согласует Алан; отметка в таблице не является уже выданным разрешением.
Для каждого доступа отдельно записать во внутреннем канале: аккаунт, среду,
согласованную роль, кто выдал и результат проверки входа.

| Система | Для чего | Что передать или выдать Эрмеку | Где используется в проекте |
|---|---|---|---|
| GitHub | Код, ветки, commits/PR | Приглашение личному аккаунту; согласованная рабочая ветка | Репозиторий выше |
| Панель Frunze Travel | Диалоги, услуги, задачи | Персональный логин и отдельно согласованная роль; пароль защищённым каналом | Вход: `https://frunzetravel.kg/admin/login`; `MANAGERS`, `ADMIN_USER`, `ADMIN_PASSWORD` |
| Сервер / SSH | Логи, состояние приложения, согласованные операции | Адрес, имя пользователя и fingerprint сервера — отдельно; Эрмек передаёт свой **публичный** SSH-ключ, приватный остаётся у него | Инфраструктурные сведения у Алана; `scripts/deploy_prod.sh`, `scripts/rollback_prod.sh` |
| Кабинет хостинга | Управление VPS и восстановление | Отдельный аккаунт/приглашение, если входит в обязанности; актуального провайдера уточнить у Алана | Не определяется из кода приложения |
| DNS / домен | Записи домена, HTTPS | Доступ к нужной зоне по согласованию; текущий кабинет и владельца уточнить | `frunzetravel.kg`; старые документы упоминают Cloudflare, актуальность не проверена |
| PostgreSQL | Данные приложения | Для разработки собственная тестовая БД; production-доступ и сетевой маршрут выдаются отдельно | `DATABASE_URL`, `POSTGRES_PASSWORD`; PostgreSQL 16 в compose |
| Redis | Состояния диалогов, временные ключи | Собственный тестовый экземпляр; production-подключение только по согласованию | `REDIS_URL`; Redis 7 в compose |
| Wappi Pro | WhatsApp-каналы, профили, webhooks | Доступ в нужный кабинет, API token и согласованные профили; тестовый канал согласовать отдельно | `WAPPI_TOKEN`, `WAPPI_BASE_URL`, `BOTS`, legacy `WAPPI_PROFILE_ID` |
| Bitrix24 | CRM, открытые линии, сделки | Приглашение в фактический портал, роли и интеграционные права; webhook URL передать целиком защищённым каналом | `BITRIX24_WEBHOOK_URL`, `BITRIX_PORTAL_URL`, `BOTS`, `BITRIX_*` mappings |
| OpenRouter | Ответы языковой модели | Ключ для согласованной среды и лимит расходов; кабинет нужен отдельно, если Эрмек следит за балансом | `OPENROUTER_API_KEY`; настройки моделей и бюджета в `app/config.py` |
| Anthropic API | Прямое подключение, если используется | Уточнить необходимость; не обязательный доступ для офлайн-разработки | `ANTHROPIC_API_KEY`; один из прежних env/compose гейтов требует отдельной проверки |
| Telegram: тестовые боты | Проверка диалогов | Отдельный тестовый бот и токен; не подключать второй polling-процесс к рабочему боту | `TELEGRAM_BOT_TOKEN` либо `TELEGRAM_BOTS` |
| Telegram: уведомления | Оповещения менеджерам | Доступ в согласованные рабочие чаты; токен бота и chat IDs только при необходимости сопровождения | `MANAGERS_TELEGRAM_BOT_TOKEN`, `MANAGERS_TELEGRAM_CHAT_ID`, `OPS_ALERT_CHAT_IDS` |
| TourVisor | Поиск туров | Выделенные или согласованные интеграционные login/password; кабинет и договорные ограничения уточнить у Алана | `TOURVISOR_LOGIN`, `TOURVISOR_PASS` |
| Распознавание речи | Обработка голосовых | Ключ выбранного STT-провайдера и согласованный лимит; для обычных тестов не нужен | `STT_API_KEY`, `STT_PROVIDER`, `STT_BASE_URL` |
| Секреты приложения | Сессии и проверка webhooks | Для dev сгенерировать собственные; рабочие значения передавать только ответственному за сопровождение | `SESSION_SECRET`, `WEBHOOK_SECRET` |
| Исходные материалы | Требования, PDF, принятые решения | Алан передаёт нужные исходники отдельно и указывает актуальные версии | `Kyrgyzstan-visa-knowledge-base-v1.1.pdf` хранится вне Git; производные документы не заменяют оригинал |

уточнить у Алана; актуальное использование панели этой проверкой не подтверждено.

## 3. Как передать секреты

Рабочие значения находятся в серверном `prod.env` вне Git; локальный `.env` может
содержать только часть настроек и не является полной копией production. `.env.example`
также неполон: точные имена и типы настроек проверять в `app/config.py`.

Алан передаёт необходимые значения через согласованное защищённое хранилище или
канал с ограничением получателя. Адрес/приглашение в такое хранилище ещё не указан.
В GitHub оставить только эту инструкцию, названия переменных и статус выдачи.
Полный Bitrix webhook URL, DSN с паролем, JSON `MANAGERS`/`TELEGRAM_BOTS` и ссылка
с секретом в query string тоже считаются секретами, даже если выглядят как настройки.

В чистом рабочем каталоге локальный `.env` исключён через `.gitignore`; проверить
это командой `git check-ignore .env` перед добавлением файлов. На `prod.env` такое
исключение в текущем корневом `.gitignore` **не распространяется**: серверный файл
не копировать в отслеживаемое дерево. Не сохранять выдаваемые значения в issues,
PR, commits, скриншотах или документах этого публичного репозитория.

## 4. Начало локальной работы

Python 3.12, Git. Docker нужен для локальных PostgreSQL/Redis и интеграционных задач;
для первого чтения кода и офлайн-тестов рабочие доступы к внешним сервисам не нужны.
Следующие команды создают **новый** каталог, не предназначены для существующего checkout:

```powershell
git clone --branch fix/tours-search-quality https://github.com/Ulfacar/frunze-travel-bot.git frunze-travel-bot
cd frunze-travel-bot
git rev-parse --short HEAD
py -3.12 -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r requirements.txt
.\.venv\Scripts\python.exe -m pip install pytest pytest-asyncio
```

Сверить полученную ревизию с Аланом. Для нового чистого dev-каталога можно создать
собственный `.env` с backend `STATE_BACKEND=memory`, `CRM_BACKEND=stub`,
`PANEL_BACKEND=memory`; внешние ключи оставить пустыми, `BOTS=[]`, `TELEGRAM_BOTS=[]`,
`MANAGERS=[]`, `DEMO_LOGIN=false`. Это отправная конфигурация для локальной работы,
не production-конфигурация и не изоляция всех сетевых вызовов.

```powershell
.\.venv\Scripts\python.exe -m pytest tests -q
```

Запускать pytest именно для `tests`, не из всего дерева: в `runs/` есть временные
каталоги. Часть проверок требует исходный PDF вне Git. Обычные тесты используют
`tests/conftest.py` с ограничением внешних Python socket-вызовов; флаг
`--allow-external-network` не нужен для обычной проверки. Это не защита subprocess.

При тестировании интерфейса настроить собственные dev-логин, пароль и session secret.
`SESSION_HTTPS_ONLY=false` допустим только для локального HTTP. Запуск приложения
включает фоновые задачи, поэтому нельзя запускать локальную копию с рабочим `prod.env`.
Для Telegram-диалога использовать отдельного тестового бота; рабочие WhatsApp-номера,
Bitrix и реальные клиентские записи не использовать как песочницу.
