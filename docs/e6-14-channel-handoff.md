# E6-14 exact WhatsApp dialogue stop — local contract

CRITICAL, reviewed local synthetic target. Source: PDF Appendix B4/B6 and fixed engineering B04/H04; no change to their definitions or weights. The independent pre-audit is `ai/reviews/2026-10-11-e6-14-pre-audit.md`. This document specifies behavior, not review approval or production acceptance.

An existing full administrator selects an existing WhatsApp Dialog of the service-case contact, reviews the actual Wappi endpoint/profile/private recipient, and explicitly confirms a permanent autonomous-send stop. A contact can be a payer or representative: this operation grants no right to disclose applicant data and sends no message. One immutable record binds the exact interview, applicant, case, contact, Dialog, handoff card/event, operator, policy, preview and request. Active/paused interviews produce a handoff in the same transaction; pending/acked cards retain their existing history. The original owner/card-hash acknowledgement remains separate in the interview page.

The current entry point is the native full-admin form linked from the interview. Legacy LLM handoffs, every PDF escalation trigger, all old interviews, and every channel of a contact are not automatically enrolled. Telegram and Bitrix enrollment is unavailable: their existing phone-normalized shadow Dialog keys are insufficient proof of actual provider chat identity. WhatsApp groups and unsupported address forms are also unavailable. These limits remain visible in source coverage and scoring.

## Identity and authority

The versioned route is HTTPS provider origin + actual resolved Wappi profile + exact private recipient digits. Only the adapter's supported optional `@c.us` spelling is equivalent. No country-code guessing, punctuation stripping, Telegram sender/chat inference or Bitrix phone/dialog inference. Logical aliases and global profile fallback resolve to the same route and lock. Enrollment resolves trusted server configuration from an existing known bot. Sending snapshots the Wappi instance's scalar route configuration and the message destination before awaits; its existing provider client is shared. The same captured instance/destination is used by the guard and actual provider call, including across the awaited pending log. Its descriptor is also rechecked before invoking the callback. Secret-bearing origins are rejected; tokens are never stored in the route.

Two settings default empty: `kg_channel_guard_scopes` explicitly activates provider account protection; `kg_channel_stop_policy` pins authority/privacy evidence, allowed existing full administrators, permitted scope hashes and validity dates. Expiry/removal of the business policy never clears a stored stop. Removing an account from deployment activation disables enforcement for that account and is an explicit operational rollback outside this task. The native current view distinguishes active enforcement, deactivated protection and invalid configuration. No real policy, account or recipient is supplied by fixtures.

Current existing full-admin identity is checked before DB access, including exact retries. A prior exact request returns the original immutable receipt after policy removal; changed target, revision or request conflicts. New enrollment locks and rereads the case and Dialog, then samples a fresh timestamp and checks scope/policy validity, exact preview/day/revision and contact identity. That same timestamp is used for the handoff and binding; waiting for either row lock cannot retain yesterday's policy or preview. Existing stops cannot be reset, rebound or removed through this feature. ACK, later interview corrections, legacy interception expiry/reset and changed mutable Dialog fields cannot clear the pinned route.

## Admission and integrity

PostgreSQL shared send and exclusive binding advisory locks use a stable SHA256-derived signed int64 namespace and are obtained before the registry lookup, including when no binding exists. Writer order is route → global capacity lock → case → Dialog. Lock wait is bounded at two seconds. SQLite rehearsals use physical `BEGIN IMMEDIATE` and bounded busy timeout; they are not substitute evidence for PostgreSQL races.

The provider callback is outside every retry helper. The sender owns a non-retrying session, holds admission through the callback, bounds that callback at 25 seconds and releases the read transaction by rollback. Exceptions, timeout, cancellation and cleanup uncertainty cannot automatically invoke the callback again. The guarantee is one local callback invocation at most per admitted operation, not exactly-once remote delivery or recall of an already submitted provider request. If an invoked callback or its cleanup fails, the outcome is an exception/unknown, not a successful suppressed result. Normal provider `None` remains distinct from suppression.

Every activated negative lookup validates the entire registry, bounded to 128 rows, 64 KiB canonical payload per row and 4 MiB total. SQL length checks reject oversized JSON before fetching/decoding it; canonical byte checks enforce final limits. The global writer lock serializes capacity across different routes/cases. Full capacity permits reads, suppression and exact retries but rejects a new stop. Overflow/corruption blocks all activated accounts; this intentionally trades availability for a reliable negative answer. The bounded registry is suitable for this local pilot slice, not a claim of unlimited fleet scalability.

Routing columns are checked against immutable payloads, source/preview pins, actual scoped interview/header/events and card hashes. The card-creating transition is replayed with its retained reducer and pinned policy/catalog. Strict canonical comparison rejects bool/integer substitution. Oversized/corrupt anchors, moved routing keys and malformed activation fail closed. Hashes cannot authenticate a database against an actor able to replace/delete all records and their trust anchors.

## Installed behavior and interface

`Orchestrator._reply` and automated outbound used by scheduled/manual-triggered followups have the final gate. Early turn/media checks also avoid needless generation for already stopped routes. The final gate catches work started before enrollment. Suppressed callbacks create no outgoing pending/sent log, reply count, provider invocation, outbound mirror, followup count/touch or promised-reply manager notification. Human manager replies and staff alert paths retain their existing routing and authorization. Inbound logging and earlier unrelated legacy CRM/tool effects are outside the claimed cessation boundary.

The native form has existing KG/full-admin/workday/write gates, a bounded 16 KiB streaming body, strict duplicate/field checks, 64-hex CSRF/HMAC and a signed exact save envelope. The user selects a stored Dialog, never a free-form recipient. A separate unchecked confirmation is required after preview. Unknown commit results preserve the entire original signed retry even when rereading storage fails. The page works without JavaScript and shows stored stops independently of the historical interview field `channel_suppression='not_integrated'`, which is never rewritten.

Migration `e6_channel_stops_0031` only adds the immutable table and scoped constraints. Empty downgrade obtains a write/exclusive lock; populated or offline downgrade refuses. Local PostgreSQL recovery uses binary COPY into a fresh migrated schema with FKs enabled and sequence state restored. Native `pg_dump` remains blocked by Windows App Control; this work neither disables that control nor claims a production backup.

Completion requires actual installed-path, concurrency, recovery, browser and negative checks plus independent review and a separate final audit. Only their evidenced supported scope may earn B04/H04; whole-project release and all-channel completion remain separate.
