> Составлено 31.07.2026 по итогам разбора на живом проде: боевые логи `search_tours` за 7 дней,
> диалоги из БД, прямые замеры TourVisor с прод-ключей. Дефекты не гипотетические — каждый
> воспроизведён.

## 0. Что именно сломано (подтверждено замерами)

| # | Дефект | Доказательство |
|---|---|---|
| D1 | Даты клиента не доходят до API | LLM шлёт `dates:"10-16 августа"`, `_parse_dates` берёт только `dd.mm` → параметр молча выпадает. Турция: без дат → вылет 06.08, 8 ноч, 3498 EUR; с датами → 15.08, 6 ноч, 2549 EUR |
| D2 | Курорт не резолвится в страну | `resolve_country`: Пхукет/Хургада/Анталья/Дубай/Бали → `None`. Запрос уходит **без страны** → поиск по миру. Живой диалог: просили Пхукет, бот показал Шарм-эль-Шейх |
| D3 | Нет инвентаря из Бишкека | Из Бишкека реально есть Турция(85)/ОАЭ(57)/Азербайджан(73)/Мальдивы(33). Египет/Таиланд/Кипр/Вьетнам/Грузия = **0**. Из Алматы есть всё. Все 5 боевых поисков за неделю — по недоступным направлениям |
| D4 | Инструмент отдаёт голое «не нашлось» | LLM без фактов выдумывает причину: «август дорогой, поднимите бюджет». Клиент Муниса поднимала бюджет дважды впустую и ушла |
| D5 | Бюджет как жёсткий потолок в чужой валюте | Выдача в **EUR**, бюджет уходит числом как есть. «500 тыс. сом» → `priceto=500` EUR → пусто |
| D6 | Нет даты вылета в выдаче | `_format_hotels` не печатает `flydate` — подмену дат не видит ни клиент, ни менеджер, ни бот |
| D7 | Звёздность и ночи недоступны модели | `_build_query` читает `hotel_stars`/`nights`, но их **нет в схеме** `search_tours` |
| D8 | Липкая квалификация | `state.qualification.update()` копит параметры между поисками |
| D9 | Таймаут опроса 20 с мал | Замер: поиск по Египту досчитался за 53 с |

## 1. Критерий приёмки

Готово, когда на боевых входах из логов:
1. В `search.php` **всегда** уходит `country`; без страны запрос не отправляется вообще.
2. Даты клиента доезжают до API либо агент получает явный отказ «не понял даты».
3. Пустая выдача сопровождается **машинной причиной** (нет направления из города вылета / нет на эти даты / нет под фильтры), и бот озвучивает именно её.
4. Направление, которого нет из Бишкека, автоматически проверяется из Алматы (правило уже в `branding.py:59`).
5. В каждой строке выдачи есть дата вылета и валюта.
6. Бюджет никогда не приводит к пустой выдаче — он размечает, а не режет.

## 2. Этапы

### Этап 0 — тест-сеть на РЕАЛЬНЫХ входах *(делаем первым)*
План 30.06 предписывал это и был пропущен — поэтому чинили по одному симптому со скриншота.
- `tests/test_tourvisor_query.py`: табличные тесты `_build_query` на 5 боевых наборах args,
  снятых из прод-логов (Египет+Хургада, Пхукет×2, Кипр, «8-10 сентября»).
- Мокаем справочники — сети в тестах нет.
- Тесты пишутся **красными**: фиксируют желаемое поведение, а не текущее.

### Этап 1 — ядро подбора (P0: D1, D2, D3, D4, D6, D7)
1. **Структурный контракт инструмента.** В `search_tours` добавить `date_from`/`date_to`
   (`dd.mm.yyyy`, с примером в description), `nights_from`/`nights_to`, `adults`, `stars_from`,
   `budget_amount`+`budget_currency`. Свободный текст остаётся как запасной вход.
2. **Резолв курорта → страна.** Обратный индекс «курорт → (страна, регион)» по справочникам
   регионов популярных стран, с кэшем. Пхукет → Таиланд/Пхукет.
3. **Нет страны — нет запроса.** Возврат агенту: «направление не распознано, уточни страну».
4. **Фолбэк на Алматы.** Ноль из Бишкека → автоповтор из Алматы; в ответе честно
   «из Бишкека нет, из Алматы есть от X».
5. **Структурная диагностика вместо строки.** Инструмент возвращает: что искали, сколько
   нашли, мин. цену, причину нуля. Промпт: причину брать только отсюда, не выдумывать.
6. **Дата вылета и валюта в каждой строке** выдачи.

### Этап 2 — деньги и точность (D5, D9, ночи)
7. **Бюджет размечает, а не режет.** Убрать `priceto` из запроса (TourVisor и так отдаёт по
   возрастанию цены); «укладывается / выше на X» считать у себя. Убивает ложное «под бюджет
   ничего нет» и снимает валютный риск из запроса.
8. **Валюта бюджета.** Явное поле от модели + конвертация по курсам из конфига для разметки.
9. **Ночи из диапазона дат**, если не заданы явно.
10. **Таймаут опроса** 20 → 45 с с ранней отдачей, как только есть отели.

### Этап 3 — чтобы не повторилось (D8, наблюдаемость)
11. **Развести память и параметры поиска**: `qualification` — досье клиента, параметры запроса
    собираются из args текущего вызова.
12. **Метрики подбора**: поисков всего / с нулём / без страны / без дат; алерт при всплеске
    нулевых. Сейчас считается расход квоты, но не результат.

### Этап 4 — голос: снять тупик №1 по частоте
Самый частый ответ бота за 2 суток — «Голосовые сообщения пока не распознаём» (10 раз)
и «вам удобнее голосом, передаю менеджеру» (4). В WhatsApp в Бишкеке голос — норма, а не
исключение. Расшифровка (STT) числится в приоритетах с 16.07 и не сделана.
- Wappi отдаёт ссылку на .ogg → прогон через STT → дальше обычный текстовый ход.
- Голос перестаёт быть хендоффом и становится обычной репликой.

## 4. Порядок и риск
Этапы 0–1 закрывают жалобу Гриши и все потерянные диалоги из разбора. Этап 2 — про деньги.
Этап 3 — страховка от повторения. Этап 4 — голос, самый частый тупик.
Флаг не нужен: правки не меняют внешний контракт, а тест-сеть и 665 существующих тестов
держат регресс.

## 5. Осознанно вне плана
Менеджеры перехватывают 53% диалогов — это, судя по всему, штатная дневная работа, а не
дефект. Но следствие учитываем: улучшения бота множатся на 0,47.
