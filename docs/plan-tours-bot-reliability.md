# Мастер-план: тур-бот надёжно выполняет свою задачу (поиск и подбор)

> Планирует/ревьюит: Claude. Кодит: Codex. Охват: ТУР-бот (поиск/подбор). Подход: сначала
> тест-сеть, потом правки — чтобы перестать латать по одному. Составлено 30.06.2026 по итогам
> реальных ТГ-диалогов и диагностики API TourVisor.

## 1. Что значит «бот нормально работает» (критерии приёмки)
Тур-бот должен: поприветствовать → собрать минимум (направление/курорт, состав+возраст детей,
даты, бюджет, питание) → найти РЕАЛЬНЫЕ туры в TourVisor → показать 3–5 вариантов с ценами и
дисклеймером → вести к брони (офис/менеджер).

Измеримые критерии:
- На корректный семейный/пляжный запрос по доступному направлению бот возвращает ≥1 реальный
  отель с ценой (а не сразу «передаю менеджеру»).
- Никаких «Поиск временно недоступен», кроме реального сбоя API.
- Если результатов 0 из-за ограничений (бюджет/даты/курорт) — бот ЧЕСТНО объясняет причину и
  предлагает конкретную корректировку, а не слепой хендофф.
- Цены всегда с дисклеймером и только из TourVisor (без выдумок).

## 2. Карта дефектов (приоритезировано)
**P0 — ломает выдачу:**
- ✅ [задеплоено] нет возрастов детей → 0 отелей (`childage1..N`).
- ✅ [задеплоено] нет фильтра курорт/питание → «только Стамбул» (`regions`/`meal`).
- 🔧 [фикс готов, НЕ задеплоен] даты с прошлым годом → `dateto - bad format` → исключение →
  «временно недоступно». Правка в `_parse_dates` (перенос на будущий год).
- ⬜ низкий бюджет → пустая выдача → тупик. Нужен честный over-budget ответ.

**P1 — качество подбора:**
- Ночи не выводятся из явного диапазона дат (берётся дефолт 7–10). Надо: из `datefrom..dateto`.
- Бюджет: «на двоих/на всех» vs на человека; валюта (`priceto` в валюте выдачи — USD/EUR).
- Бот слишком охотно уходит к менеджеру на пустой выдаче (правило в промпте + код).
- Часть поисков упирается в таймаут опроса (20с) — вернуть частичный результат/тюнинг.

**P2 — устойчивость:**
- «к морю» без курорта → подставлять популярные курорты; несколько регионов через запятую.
- «нормальный отель» → фильтр звёздности 4–5*.
- Сортировка/дедуп: лучшая цена на отель, без повторов.

## 3. Целевое поведение поиска
- `_build_query` — единая защищённая сборка: даты в будущем, возрасты детей, курорт, питание,
  ночи из диапазона, бюджет+валюта, звёзды. Невалидные/прошлые значения чинятся, а не падают.
- `search()` — если пусто И был применён «мягкий» фильтр (цена/курорт/звёзды), сделать повторный
  проход с ослабленным фильтром и пометить результат (`over_budget` / `relaxed`), чтобы агент
  подал честно.
- `_tours_exec_tool` — возвращать LLM структурную подсказку («найдено N; мин. цена X; выше
  бюджета на Y»), чтобы бот говорил правду, а не «не нашлось».

## 4. Тест-сеть (3 уровня) — СТРОИМ ПЕРВОЙ
Сейчас на TourVisor-клиент НЕТ юнит-тестов — поэтому баги и пролезали. Тренажёр: `scripts/run_scenarios.py`
+ `scenarios/frunze_v1.json`.

- **L1 — юнит (быстро, без сети/LLM):** новый `tests/test_tourvisor.py`.
  - Табличные тесты парсеров: `_parse_dates` (прошлый год→будущий, диапазон, без года),
    `_parse_tourists` (возрасты, «3 детей»→дефолты, >4 обрезка), `_parse_meal`, `_parse_budget`,
    `_parse_nights` (вкл. вывод из диапазона дат).
  - `_build_query` с замоканными справочниками (departure/country/region) → проверять ТОЧНЫЕ
    параметры для канонных кейсов: семья Анталья AI; прошлые даты; низкий бюджет; «к морю».
- **L2 — live-smoke (сеть, без LLM):** `tests/test_tourvisor_live.py`, помечен `@pytest.mark.live`,
  гейт по кредам (skip без них). Канонные запросы → assert непусто и регион/питание совпадают.
  Ловит дрейф контракта API (где и были реальные баги). Гонять перед деплоем.
- **L3 — диалоговые сценарии (`run_scenarios.py`, нужен LLM-ключ):** добавить в
  `scenarios/frunze_v1.json` кейсы из реальных провалов: (а) семья с детьми; (б) «к морю + всё
  включено»; (в) низкий бюджет; (г) даты без/с прошлым годом; (д) «а других стран нет?».
  Rule-судья проверяет: показаны отели с ценой ЛИБО честное сообщение про бюджет; нет «временно
  недоступно»; нет выдуманных цен.

## 5. Пошаговый план (Codex кодит, Claude ревьюит каждую фазу)
- **Фаза 0 — сеть безопасности:** L1-юниты + L2-smoke вокруг ТЕКУЩЕГО поведения (зафиксировать уже
  задеплоенные childage/region/meal). Цель — зелёная база до правок.
- **Фаза 1 — даты:** ревью+тест дата-фикса (уже в рабочей копии) + ночи из диапазона. Деплой.
- **Фаза 2 — бюджет:** over-budget повторный проход + честное сообщение + тесты. Деплой.
- **Фаза 3 — подбор:** валюта/«на всех», звёзды из «нормальный отель», хендофф только при реально
  пустой выдаче (промпт+код). Тесты. Деплой.
- **Фаза 4 — полировка:** таймаут/частичный результат, мультирегион, сортировка/дедуп.
Каждая фаза: зелёные L1+L2 → деплой → точечная проверка L3.

## 6. Definition of Done
- L1-юниты + L2-smoke зелёные; L3-сценарии проходят проверки по поиску.
- Повтор 4 сегодняшних провальных диалогов → каждый теперь даёт отели или честную подсказку по
  бюджету; «временно недоступно» отсутствует.

## 7. Деплой (как у Claude)
Не git. Заменить файлы в `/root/frunze-travel/app/`, бэкап `cp -r app app.bak.$(date +%Y%m%d-%H%M%S)`,
слать в LF (`tr -d '\r'`), сверять `diff --strip-trailing-cr`, затем
`docker compose -f docker-compose.yml -f docker-compose.vps.yml --env-file prod.env up -d --build app`.
