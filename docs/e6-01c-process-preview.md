# E6-01C — проверка черновых переходов V/W/R/U

10.10.2026 · STANDARD / solo · локальная проверка для согласования процессов.
В CRM: анкета въезда → **Проверка черновых процессов**.

## Что добавлено

Версия `pdf-1.1-review-1` сохраняет все 87 кодов §§14.2–14.6 исходного PDF:
25 V +15 X,22 W +4 WX,8 R +2 RX,9 U +2 UX. У каждого есть название, исходный
текст, раздел и физическая страница63–66. V11, X10 и X12 отмечены как параллельные
флаги, а не обязательные линейные этапы. Подписи R/U сокращены для интерфейса;
полные исходные абзацы сохранены рядом. Фиксация текста не утверждает его актуальность.

Для 71 варианта переходов описаны черновые условия. Явная последовательность из PDF отличается
от предложенных связей, особенно в рабочем процессе W, где таблица не задаёт все
стрелки. **Все** формализованные обязательные факты пока являются проектом для
согласования. Коды, для которых выходы не описаны, не получают разрешение на переход.
Все исключения представлены в справочнике, но не все реализованы как переходы.

Проверка трёхзначная: неизвестный факт → «не хватает сведений»; факт, противоречащий
условию → «условия не выполнены»; все нужные факты → «выполнены в сценарии».
Последний результат всё равно имеет `execution_allowed=false`: это не исполнение
реальной заявки, не разрешение на подачу и не опубликованный процесс.

Примеры:

- V14→V15 проверяет согласие, принятие актуального комплекта и создание черновика;
  старое принятие после смены паспорта/документов не проходит как актуальное.
- V15→V16 дополнительно требует подтверждения e-mail, портальной оплаты,
  фактической отправки и номера. Эти ответы вводятся условно, не читаются из оплат.
- V18→V19 обозначает исправление той же попытки. Для X01 обратного перевода на
  рассмотрение нет: интерфейс напоминает о новой связанной заявке после анализа.
- Одобрение не заменяет проверку документа, передачу/получение и фактический въезд.
  Плановая дата въезда не является фактом.
- W15→W16 относится к отдельной заявке на резидент-карту. Рабочий процесс содержит
  и общие шаги работодателя, поэтому его нельзя целиком назначить одному документу.
- Для U05→U06 есть пути L и регистрации. Выбор регистрации не допускает U06→U07,
  даже если ошибочно указано одобрение L; нужна отдельная регистрационная процедура.
- Неизвестная возможность продукта не означает «невозможно оформить».

## Версия, форма и границы

`scripts/build_kg_process_catalog.py` воспроизводит JSON из конверсии PDF и явных
черновых описаний фактов/переходов. Метаданные сохраняют SHA256 оригинала и пяти
разделов. `app/knowledge/process_preview.py` проверяет закреплённый SHA256 каталога,
полноту кодов и связи. Для Windows нормализуются только CRLF; содержимое JSON не
переписывается. Каталог неизменяем, выдаваемые словари отделены от оригинала.

Результат закрепляет версию/хеш каталога и хеш входного сценария. Устаревшая форма
отклоняется409. Изменение/повреждение каталога —503, без результата. Недопустимые
типы, чужие коды процесса, неизвестные поля и попытка передать публикацию — ошибка.
Ввод допускает только выбор из списков: неизвестно/да/нет или именованный вариант.
ФИО, номера паспортов, суммы, файлы и другие персональные сведения не запрашиваются.

GET/POST используют прежние full-admin/KG-OFF/workday gates. POST имеет CSRF и
ограничение8 KiB; факты не сохраняются в БД/сессии и не передаются во внешний сервис.
Просмотр работает при выключенной записи. Печать содержит условия, источник,
версию и явное отсутствие разрешения на выполнение. Экран работает без JavaScript.
JSON включён в Dockerfile; сборка образа этим фактом не подтверждается.

Нет новых таблиц, публикации WorkflowVersion, изменения ServiceCase/Application,
денежных операций, вычисления юридических сроков или автоматических сообщений.
Следующий этап — согласование формализованных правил, доказательства обязательных
фактов и привязка к реальным стадиям; нужны прежние DEC-02/06/07/08/11/12 и CRITICAL
review/audit/PG gates. Полный PDF и четыре исполняемых процесса ещё не завершены.
Проверки и точная ревизия находятся в handoff из `ai/STATE.md`.
