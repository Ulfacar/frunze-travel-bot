# Техническое приложение к ТЗ

Проектные решения для реализации, 03.10.2026. Основание — [ТЗ](../spec-crm-frunze-getvisa-2026-10-03.md), разделы 3–6, 9–15. Названия новых объектов и полей ниже предлагаемые; утверждённый смысл важнее имени класса. Реальных миграций и новых API в рамках подготовки документа не создавалось.

## 1 Границы и связи

Канал → существующий Dialog/Contact/Request → отдельные ServiceCase → этапы, события, документы, деньги и задачи. Клиент может иметь несколько услуг; ограничение одного активного Request на направление сохраняет смысл входного обращения, но не ограничивает число услуг. Для семьи/работодателя ServiceCase содержит несколько Applicant, каждый может иметь несколько Application.

Действующий стек: FastAPI, SQLAlchemy/Alembic, PostgreSQL, Redis, Jinja. Источником финансовых событий, задач и намерений отправки является БД. Redis не становится единственным местом хранения обязательства. Внешний API вызывается после завершения транзакции; недоступность LLM не останавливает ведение услуги.

## 2 Основные данные и ограничения

| Объект | Минимальные поля | Инвариант |
|---|---|---|
| Product | code, direction, name, active, current_workflow_version | Используемый продукт архивируется; code не меняет смысл |
| WorkflowVersion | product_id, version, state_schema, transitions, published_by, published_at | Опубликованная версия неизменяема; активные услуги не мигрируют молча |
| ServiceCase | id, contact_id, request_id?, product_id, workflow_version, owner_id, stage, outcome, waiting_party, waiting_since, next_check_at, revision | Один клиент — много услуг; request_id необязателен при ручном договоре; доступ проверяется по направлению и назначению |
| Contract | service_case_id, reference, signed_at?, signed_by_actor?, status, agreed_amount?, currency?, amount_unknown_reason? | Отправленный договор не равен подписанному; неизвестная сумма не равна нулю |
| ServiceEvent | id, case_id, event_type, actor_id, occurred_at, recorded_at, source, operation_key, payload_version, payload | Аудит не перезаписывается; запись не хранит лишние паспортные данные |
| BookingAttempt | case_id, attempt_no, operator_ref, offer_snapshot, status, submitted_at, confirmed_at?, reason?, buyout_deadline? | Переподбор создаёт новую попытку, прежние оплаты остаются у услуги |
| TripSegment | case_id, sequence, flight_number, origin, destination, departure_local, timezone, departure_utc, checkin_open_at?, checkin_close_at?, confirmed_by | Изменение рейса версионируется; время не вычисляется по одному названию города |
| PaymentEntry | case_id, operation_id, kind, original_amount, currency, credited_amount?, contract_currency, fx_rate?, confirmed_by, effective_at, reversal_of? | Decimal/фиксированная точность; уникальный ключ операции; исправление через историю, без скрытого удаления |
| RefundRequest | case_id, reason, requested_amount, decision, approved_amount?, approver?, status, payment_entry_id? | Утверждение обязательства отдельно от факта возврата |
| Applicant | id, case_id, person_ref, nationality, passport_ref, representative_scope? | Представитель/плательщик не получает все документы автоматически |
| Application | applicant_id, product_type, workflow_version, stage, attempt_no, previous_application_id?, portal_reference?, submitted_at?, actual_result?, expected_result_at? | Результат одной процедуры не завершает все процедуры заявителя |
| DocumentVersion | subject_type/id, kind, version, storage_key, checksum, status, uploaded_by, consent_ref, expires_at?, sensitivity | Новая версия требует новой проверки; object key не является правом доступа |
| DocumentCheck | version_id, verdict, checked_by, checked_at, findings | «Получен» и «принят» различаются; проверка относится к конкретной версии |
| Task / Deadline | существующая CalendarTask плюс case_id/application_id, event_ref, rule_version, deadline_kind, due_at, timezone, status, cancellation_reason | Крайний срок, ожидаемая дата и напоминание — разные значения; выполненная задача не пересоздаётся |
| MessageIntent | event_ref, case_id, template_version, recipient_ref, scheduled_at, event_revision, operation_key, status | Перед отправкой повторная проверка актуальности, прав, перехвата, согласий и остановок |
| KnowledgeVersion / Calculation | source_version, approval, effective_from/to, input_snapshot, calendar_version, result, reason_codes | Расчёт воспроизводим; неподтверждённые/неполные данные дают явный отказ от точного вывода |

Поля с вопросительным знаком допустимы только по смыслу конкретного продукта. Отдельно различаются «неизвестно», «не применимо», ноль и false. Contract в этой таблице — логический блок договора: в первой версии его поля допустимо хранить непосредственно в ServiceCase; отдельная таблица не требуется без необходимости нескольких договоров на услугу. Типы и ограничения уточняются до первой миграции на основании реальной схемы; одна огромная JSON-карточка не заменяет индексы, связи и ограничения для денег/прав.

## 3 Команда изменения и событие

Любая мутация: действующий пользователь → проверка направления/владения/операции → проверка expected_revision → валидация обязательных фактов → транзакция изменения и записи событий/намерений → commit → ответ → независимый исполнитель внешних действий. Для запросов с cookie действует CSRF-защита. Ошибка версии — явный конфликт с предложением обновить карточку, без потери введённого текста.

Ключ операции ограничен типом операции и услугой. Повтор с тем же ключом и тем же содержимым возвращает исходный результат; тот же ключ с другими данными вызывает конфликт. Возвращаемый ранее результат выдаётся только после повторной проверки текущих прав. Ключ не заменяет ограничения БД и блокировку/версию.

| Событие | Кто подтверждает | Изменение | Зависимые действия |
|---|---|---|---|
| contract_signed | Сотрудник с правом ведения | Дата/основание продажи и создание исполнения | Начальные задачи один раз; черновик опросника для США |
| booking_submitted / confirmed / declined | Менеджер тура | Новая попытка/подтверждение/отказ | Контроль ответа, выкупа; альтернативы или возврат |
| payment_confirmed / payment_corrected | Разрешённая роль | Операция и новая проекция расчётов | Пересчёт остатка; отмена только уже ненужных задач доплаты |
| questionnaire_submitted / returned / approved | Клиент в своём доступе; проверка специалистом | Версия анкеты и подтверждения | Следующее действие; возврат отменяет актуальное подтверждение |
| interview_scheduled / rescheduled | Менеджер визы | Подтверждённая дата с поясом | Будущая подготовка/напоминания; проведённые занятия сохраняются |
| document_received / checked | Клиент/сотрудник; проверяет сотрудник | Версия файла и её статус | Чек-лист; блокировка подачи при неполном принятом комплекте |
| application_submitted / returned / decided | Сотрудник; письмо только по утверждённым правилам | Событие конкретной попытки подачи | Контроль результата/доработки; проверка выданного документа |
| owner_changed | Разрешённый администратор | Новое назначение с причиной | Все открытые задачи получают согласованного владельца |
| trip_changed / actual_entry_confirmed | Сотрудник | Новая версия плана / отдельный факт въезда | Пересчёт будущих задач; прошлые факты не стираются |
| service_cancelled / messaging_opt_out | Сотрудник / подтверждённый клиентский отказ | Причина отмены/ограничение связи | Отмена недопустимых будущих сообщений; отдельное рассмотрение расчётов |

Сигнал из текста/голоса создаёт предложение, а не подтверждает оплату, контракт, подачу и официальный результат. Шаблоны могут зависеть от результата детерминированного расчёта, но LLM не выбирает собственные суммы/даты вместо него.

## 4 Контракт экранов

| Экран | Главный вопрос пользователя | Обязательное действие | Пустота/ошибка |
|---|---|---|---|
| Рабочий день | Что сделать сейчас и почему? | Выполнить задачу, открыть услугу, перенести с причиной | «Нет задач» только при успешной загрузке; сбой виден отдельно |
| Продажи / исполнение | На каком этапе моя работа? | Выбрать продукт, фильтр, разрешённое действие | Новый продукт не появляется активным без опубликованного процесса |
| Карточка | Кто отвечает, что дальше, что мешает? | Один следующий шаг; доступ к истории/документам/оплатам | Неизвестная сумма и непроверенный документ обозначены явно |
| Календарь | Что приближается и к какому времени? | Открыть событие/услугу, изменить подтверждённую дату | Часовой пояс и источник даты; просроченная загрузка отмечена |
| Сводка | Сколько договоров, денег, задержек? | Открыть список, давший показатель | Неполнота данных отдельной метрикой; валюты не складываются |
| Знания | Какие правила действуют и где конфликт? | Сравнить черновик/активную версию, открыть источник | Ошибка импорта не меняет активную версию |
| Въездные заявки | Что готово у каждого человека? | Открыть отдельную процедуру/подачу | Группа «2 из 3», причина задержки; чужие документы не доступны |

Предложенный порядок карточки: шапка «клиент — продукт — менеджер — ближайший срок»; блок «следующее действие и причина»; готовность; вкладки «Путь / Документы / Оплаты / Задачи / Переписка»; лента истории. На телефоне основной шаг виден без горизонтального скролла. Согласование макета E0-04 должно пройти на туре, США и группе заявителей, включая пустые данные и ошибку сохранения.

## 5 Данные из старой системы

| Источник | Цель | Правило переноса |
|---|---|---|
| Conversation.bot_id + phone / ContactIdentity | Существующий Contact/Dialog и ссылка услуги | Только проверенное соответствие; имя не ключ слияния |
| Request | Источник входного обращения | Сохранять связь, не превращать все покупки клиента в один статус |
| Assignment | Ответственный | Проверить актуальность и направление; неназначенные записи в отдельный реестр |
| Conversation.sale_amount | Предварительная запись для сверки оплаты | Не считать ценой договора; не создавать второй платёж; неизвестную валюту не угадывать |
| Bitrix external ID | ExternalReference | Один Bitrix ID не доказывает одного человека в общей Открытой линии |
| Старые CalendarTask | Задачи с исходной историей | Привязать к услуге только при доказанной связи; спорные задачи не терять |
| Файлы/комментарии | Документы/события в утверждённом объёме | Сначала политика, права и карта полей; не импортировать все вложения без разбора |

Миграция: новая схема без разрушения старой → тесты на копии → пробный идемпотентный импорт → сверка → пилот с владельцем каждого поля → согласованное переключение → сохранение карты соответствия. До окончания пилота старые факты не удаляются. Выбор параллельной записи/чтения определяется после аудита, а не назначается автоматически этим приложением.

## 6 Готовность архитектуры к реализации

До кода конкретного модуля разработчик прикладывает схему полей/переходов, проверенные существующие файлы, тестовые сценарии и план обратимости. Реализацию можно делать на синтетике при открытых бизнес-вопросах, используя явно отключённые функции. Работа с деньгами, доступами, реальными документами и переносом данных требует CRITICAL-проверки согласно AGENTS; независимое ревью не подменяется этой спецификацией.

Отдельные незакрытые технические факты E0: состояние domain/messaging shadow в действующей БД; фактический путь Wappi↔Bitrix; точность связей Contact/Dialog/Request; источник подтверждения оплаты; доступный изолированный стенд; механизм хранения документов. Ни один из них не считается проверенным только по наличию класса в коде.
