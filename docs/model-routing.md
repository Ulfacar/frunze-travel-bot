# Кто какую работу делает: Fable, Opus, Sonnet, Codex

Обновлено 05.10.2026 по разделу «Режим исполнения» нового ТЗ
(`ТЗ_Frunze_Travel_и_GetVisa_объединённое.md`, добавлен 05.10). **Таблица ролей ниже —
из ТЗ и имеет приоритет.** Прежняя версия этого документа назначала Codex автором кода;
это было нашей договорённостью до появления раздела, и она отменена.

## Роли по ТЗ

Четыре модели. Правило, которое держит всю схему: **автор и проверяющий задачи — всегда
разные модели.**

| Модель | Роль | Берёт | Не берёт |
|---|---|---|---|
| **Fable** | архитектор и финальный аудит | схема и инварианты до первой миграции, предложение по `visa_inbound`, разбор конфликтов SRC, системный промпт въездного диалога, финальный аудит CRITICAL | рутинный код и перенос таблиц |
| **Opus** | автор CRITICAL и сложной логики | права, деньги, связь старых данных, надёжные задачи и доставка, калькуляторы, импорт из Bitrix, почта | вёрстку и простые формы |
| **Sonnet** | автор STANDARD и объёма | инвентаризация данных, макеты, модели и миграции по готовой схеме, процессы продуктов, экраны, сводка, конверсия PDF | решения по архитектуре и правам |
| **Codex** (GPT-6 Astra) | независимая проверка | тесты по шагам AC, ревью каждой CRITICAL-задачи, построчная сверка данных с PDF, второй независимый проход инвентаризации Bitrix | правки чужой задачи без отдельной карточки |

Распределение по всем 35 задачам — в самом ТЗ, раздел «Задачи по моделям». Коротко:
E1-02, E1-04, E1-05, E2-03, E3-01, E4-02, E4-03, E5-03, E6-01, E6-03 и вся группа E7 —
CRITICAL, автор Opus, проверка Codex, затем аудит Fable. E2-01, E2-02, E2-06, E2-07,
E3-02, E3-03, E4-01, E5-01, E6-02 — STANDARD, автор Sonnet, проверка Codex.

## Правила связки (из ТЗ)

1. Данные из PDF: любой перенос стран, лимитов, сроков и сумм сверяется второй моделью
   построчно. **Реестр SRC первичен — конфликтующее значение не импортируется как действующее.**
2. Вход модели: карточка задачи и разделы ТЗ по их ID, а не весь файл комплекта.
   Менять можно только файлы из карточки.
3. Точка продолжения: после задачи автор обновляет состояние проекта и прикладывает
   доказательство из карточки. Статус «готово» без доказательства не ставится.
4. Люди: опросы, решения DEC, показ макета сотруднику и пилот выполняют Алан и
   сотрудники. Модель не подписывает бизнес-приёмку.

## Наши дополнения, которых в ТЗ нет

ТЗ описывает роли, но не описывает механику запуска в этой среде. Здесь она.

| Инструмент | Что это | Как запускается |
|---|---|---|
| Opus | главная модель сессии | работает напрямую |
| Codex CLI 0.160.0 | внешний Codex | `codex exec --sandbox workspace-write -C "<dir>" -`, промпт через stdin; `--sandbox read-only` для разбора без правок |
| `codex-reviewer` | субагент-ревьюер, read-only | `.claude/agents/codex-reviewer.md`, модель sonnet |
| `codex-auditor` | субагент-аудитор CRITICAL, read-only | `.claude/agents/codex-auditor.md`, модель opus |
| Sonnet / Fable / Haiku | субагенты | `model: 'sonnet' | 'fable' | 'haiku'` в вызове Agent |

`CLAUDE_CODE_SUBAGENT_MODEL` в `settings.json` не ставить: он перебивает и frontmatter,
и выбор при вызове — тогда ревьюер с аудитором тоже уедут на дешёвую модель.

**Роль Fable «финальный аудит CRITICAL» закрывается двумя способами:** субагентом Fable
напрямую либо `codex-auditor` на Opus. Второй уже показал себя: на E1-01 он поднял
PostgreSQL 16 в докере, воспроизвёл накат миграции на прод-подобной базе и нашёл мину в
ревизиях от 19 августа. Выбор между ними — по характеру задачи: схема и инварианты к
Fable, поведение на боевой базе к аудитору.

## Ограничители, выстраданные этим проектом

1. **Сверяю диф, а не отчёт.** Отчёты уже перечисляли как «сделано» предохранители,
   которых в коде не было. Перед прод-действием читаю сам диф или хеш файла.
2. **Числа агента перепроверяю сам.** «45 passed» бывает про другой файл.
3. **Ревьюер не видит отчёт автора до своего первого вердикта.**
4. **Разные вендоры сами по себе не дают независимости** — её даёт отдельный контекст и
   то, что проверяющий не писал код.
5. **Fable, Sonnet и Haiku не допускаются** к решениям о деньгах, правах и бизнес-политике,
   к прод-действиям и к включению флагов. Их выход — материал, который проверяю я.
6. **Прод трогаю только я и только по слову Алана.** Субагентам прод-действия не поручаются;
   чтение прода допустимо, запись — нет.
7. **Класс C без аудита не выкатывается.** Нет аудита — статус PARTIALLY_READY.
8. **Спека автору включает блок project gotchas**: часовые пояса и дата Бишкека, per-bot
   флаги поверх глобального, перехват менеджером, `childage1..N` у TourVisor, офис пн–сб,
   `sale_amount` — это оплата, а не цена договора.

## Что было сделано до перехода на режим ТЗ

Эти задачи шли по прежней договорённости, где код писал Codex. Решением Алана 05.10
принимаются как есть, не переделываются:

- **E0-02** — замер доменного слоя (автор Opus вместо Sonnet, сверки Codex не было).
- **E0-03** — инвентаризация Bitrix (автор Sonnet вместо Opus; второй независимый проход
  Codex запланирован отдельно, как требует ТЗ).
- **E0-04** — макет карточки услуги (автор Fable вместо Sonnet).
- **E1-01** — продукты, версии процессов, услуга (автор Codex вместо связки Fable+Sonnet).
  Прошёл ревью, аудит на живом PostgreSQL 16 и 1973 теста. Правило «автор ≠ проверяющий»
  соблюдено.
- Работы по панели (Фокус, чат «Пальма», контраст, обёртка таблиц) — вне 35 задач ТЗ.
