## Схема 28.10.2026 — действующая

**Ведущий — Opus, из терминала Claude Code.** Остальных вызывает он сам.

| Кто | Чем является | Берёт | Как запускается |
|---|---|---|---|
| **Opus** | главная модель сессии, ведущий | класс риска, ТЗ, гейт, свой код, ревью кода Codex, прод-действия по слову Алана | работает напрямую |
| **Codex** (`gpt-6-astra`) | **внешний вендор, OpenAI** | DevOps, CI, свой код по ТЗ, независимое ревью кода Claude, эталоны тестов по тексту ТЗ/PDF | `codex exec -m gpt-6-astra --sandbox read-only⎮workspace-write -C "<каталог>" -`, промпт через stdin |
| **Sonnet** | субагент Claude | объём: инвентаризация, перебор, массовые правки по готовой схеме | `Agent(model: 'sonnet')` |
| **Fable** | субагент Claude | архитектура, инварианты, аудит класса CRITICAL | `Agent(model: 'fable')` |

**Правило вендоров.** Автор и проверяющий — всегда разных вендоров: код Claude проверяет
Codex; код Codex проверяет Opus или Fable. Codex не ревьюит сам себя, Claude не ревьюит
сам себя.

**Если Codex не отвечает** — проверяет другая модель Claude, и ревью помечается
**«без кросс-вендора»**. Работа при этом не стоит: отсутствие Codex — это пометка в
отчёте, а не блокер.

**Прод, деплой и флаги — только по слову Алана.** Codex на прод не ходит ни при каких
условиях: он готовит команды и скрипты, выполняет Opus после «да». Субагентам Claude
прод-действия тоже не поручаются; чтение прода допустимо, запись — нет.

### Кто такие `codex-reviewer` и `codex-auditor` — важная поправка

Их **нет в репозитории**. Они лежат у Алана на машине, на уровне пользователя:

```
C:\Users\alanb\.claude\agents\codex-reviewer.md   # frontmatter: model: sonnet
C:\Users\alanb\.claude\agents\codex-auditor.md    # frontmatter: model: opus
```

Это **субагенты Claude**, а не Codex. Имя обманывает: оно значило «ревьюер кода, который
написал Codex», а не «ревьюер на модели Codex». Поэтому:

> **Все прежние ревью и аудиты, подписанные `codex-reviewer` и `codex-auditor`,
> делал Claude.** Кросс-вендорной независимости в них не было — Claude проверял Claude.
> Это относится в том числе к `publication_review` и `e622_audit` по отдельной CRM,
> к APPROVE по J01 и GO по J03.

Два следствия, с которыми живём:
1. В каталоге `.claude/agents/` репозитория этих файлов нет, и на другой машине их не
   будет. Запись в прежней версии этого файла (`.claude/agents/codex-reviewer.md`) была
   неверной — путь пользовательский, не проектный.
2. Прежняя строка `docs/protocol.md` «`codex-reviewer` — ревью №1 (Opus, read-only)» тоже
   была неверной: в frontmatter стоит `sonnet`.

Настоящий кросс-вендорный путь ровно один — **внешний Codex CLI**: либо `codex exec` с
отдельным брифом, либо `codex review --base <ветка>` / `--uncommitted`.

Субагентами `codex-reviewer` / `codex-auditor` пользоваться можно и дальше, но в отчёте
они называются своим настоящим вендором: «ревью Claude (sonnet)», «аудит Claude (opus)»,
и при классе C они **не закрывают** требование независимого ревью в одиночку.

### Проверено 28.10.2026

```
codex --version      → codex-cli 0.163.0
codex exec -m gpt-6-astra --sandbox read-only   → работает, ответ получен
codex mcp-server     → подкоманды НЕТ (вываливается в usage)
codex mcp            → только управление ВНЕШНИМИ MCP внутри самого Codex
codex app-server     → есть, экспериментальный (JSON-RPC, daemon/proxy)
```

Отдельного режима «Codex как MCP-сервер» в 0.163.0 нет. Ничего не подключено.

## Роли по ТЗ (основание распределения 35 задач ТЗ)

Четыре модели. Правило, которое держит всю схему: **автор и проверяющий задачи — всегда
разные модели.**

| Модель | Роль | Берёт | Не берёт |
|---|---|---|---|
| **Fable** | архитектор и финальный аудит | схема и инварианты до первой миграции, предложение по `visa_inbound`, разбор конфликтов SRC, системный промпт въездного диалога, финальный аудит CRITICAL | рутинный код и перенос таблиц |
| **Opus** | автор CRITICAL и сложной логики | права, деньги, связь старых данных, надёжные задачи и доставка, калькуляторы, импорт из Bitrix, почта | вёрстку и простые формы |
| **Sonnet** | автор STANDARD и объёма | инвентаризация данных, макеты, модели и миграции по готовой схеме, процессы продуктов, экраны, сводка, конверсия PDF | решения по архитектуре и правам |
| **Codex** (GPT-6 Astra) | независимая проверка | тесты по шагам AC, ревью каждой CRITICAL-задачи, построчная сверка данных с PDF, второй независимый проход инвентаризации Bitrix | правки чужой задачи без отдельной карточки |

Распределение по всем 35 задачам — в самом ТЗ, раздел «Задачи по моделям». Коротко:
E1-02, E1-04, E1-05, E2-03, E3-01, E4-02, E4-03, E5-03, E6-01, E6-03 и вся группа E7 —
CRITICAL, автор Opus, проверка Codex, затем аудит Fable. E2-01, E2-02, E2-06, E2-07,
E3-02, E3-03, E4-01, E5-01, E6-02 — STANDARD, автор Sonnet, проверка Codex.

## Правила связки (из ТЗ)

1. Данные из PDF: любой перенос стран, лимитов, сроков и сумм сверяется второй моделью
   построчно. **Реестр SRC первичен — конфликтующее значение не импортируется как действующее.**
2. Вход модели: карточка задачи и разделы ТЗ по их ID, а не весь файл комплекта.
   Менять можно только файлы из карточки.
3. Точка продолжения: после задачи автор обновляет состояние проекта и прикладывает
   доказательство из карточки. Статус «готово» без доказательства не ставится.
4. Люди: опросы, решения DEC, показ макета сотруднику и пилот выполняют Алан и
   сотрудники. Модель не подписывает бизнес-приёмку.

## Наши дополнения, которых в ТЗ нет

ТЗ описывает роли, но не описывает механику запуска в этой среде. Здесь она.

| Инструмент | Что это | Как запускается |
|---|---|---|
| Opus | главная модель сессии | работает напрямую |
| Codex CLI 0.163.0 | внешний Codex, вендор OpenAI | `codex exec -m gpt-6-astra --sandbox workspace-write -C "<dir>" -`, промпт через stdin; `--sandbox read-only` для разбора без правок |
| `codex review` | кросс-вендорное ревью диффа от GPT | `codex review --base <ветка>` либо `codex review --uncommitted` |
| `codex-reviewer` | субагент **Claude**, ревьюер, read-only | `C:\Users\alanb\.claude\agents\codex-reviewer.md` (вне репозитория), модель **sonnet** |
| `codex-auditor` | субагент **Claude**, аудитор CRITICAL, read-only | `C:\Users\alanb\.claude\agents\codex-auditor.md` (вне репозитория), модель opus |
| Sonnet / Fable / Haiku | субагенты | `model: 'sonnet' | 'fable' | 'haiku'` в вызове Agent |

`CLAUDE_CODE_SUBAGENT_MODEL` в `settings.json` не ставить: он перебивает и frontmatter,
и выбор при вызове — тогда ревьюер с аудитором тоже уедут на дешёвую модель.

**Роль Fable «финальный аудит CRITICAL» закрывается двумя способами:** субагентом Fable
напрямую либо `codex-auditor` на Opus. Второй уже показал себя: на E1-01 он поднял
PostgreSQL 16 в докере, воспроизвёл накат миграции на прод-подобной базе и нашёл мину в
ревизиях от 19 августа. Выбор между ними — по характеру задачи: схема и инварианты к
Fable, поведение на боевой базе к аудитору.

## Ограничители, выстраданные этим проектом

1. **Сверяю диф, а не отчёт.** Отчёты уже перечисляли как «сделано» предохранители,
   которых в коде не было. Перед прод-действием читаю сам диф или хеш файла.
2. **Числа агента перепроверяю сам.** «45 passed» бывает про другой файл.
3. **Ревьюер не видит отчёт автора до своего первого вердикта.**
4. **Разные вендоры сами по себе не дают независимости** — её даёт отдельный контекст и
   то, что проверяющий не писал код. Обратное тоже верно и стоило нам доверия к отчётам:
   **один вендор независимости не даёт совсем.** Имя `codex-reviewer` маскировало это
   полгода (см. поправку выше).
5. **Fable, Sonnet и Haiku не допускаются** к решениям о деньгах, правах и бизнес-политике,
   к прод-действиям и к включению флагов. Их выход — материал, который проверяю я.
6. **Прод трогаю только я и только по слову Алана.** Субагентам прод-действия не поручаются;
   чтение прода допустимо, запись — нет.
7. **Класс C без аудита не выкатывается.** Нет аудита — статус PARTIALLY_READY.
8. **Спека автору включает блок project gotchas**: часовые пояса и дата Бишкека, per-bot
   флаги поверх глобального, перехват менеджером, `childage1..N` у TourVisor, офис пн–сб,
   `sale_amount` — это оплата, а не цена договора.
