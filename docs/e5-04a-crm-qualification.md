# E5-04A — анкета въезда в карточке CRM

09.10.2026, **CRITICAL / solo / PARTIALLY_READY**. Реализован локальный пилот для
администратора. Независимые reviewer/final auditor и PostgreSQL runtime UNKNOWN.
Общий редизайн отложен по указанию Алана; экран использует текущую оболочку CRM.

## Пользовательский путь

1. Администратор открывает существующую визовую услугу `/admin/case/{case_id}`.
2. Ссылка «Анкета въезда в Кыргызстан» ведёт на `/admin/case/{case_id}/kg-entry`.
3. Поля документа/поездки/пребывания/нарушений заполняются вручную. «Не спрашивали»,
   «Клиент не знает», «Да/Нет» и даты сохраняются раздельно. Вопросы клиенту RU/EN.
4. Сохранение создаёт неизменяемую версию E5-03E; обновление страницы показывает данные
   из БД, следующие 1–3 вопроса, недостающие ответы, причины проверки и конфликт источника.
5. Предыдущая версия доступна для чтения, «Последняя анкета» возвращает к редактированию.

Анкета **общая для контакта**, что указано в интерфейсе. Две визовые услуги одного
человека используют одну текущую квалификацию; это ещё не отдельные анкеты по заявлениям.
Ссылка доступна из существующих `visa` услуг, включая старые выездные продукты:
это инструмент клиента для поездки в Кыргызстан, **не** изменение назначения услуги.
Новое направление, продукт, Applicant/Application и четыре въездных процесса E6-01
не создаются без согласованной матрицы. Нет привязки qualification → service case в БД.

Это первый ручной CRM-путь для partial profile E5-03D, а не весь бот-диалог E5-04:
имена/контакты остаются в CRM, полные collecting/handoff слоты, приглашения, группы,
суммы, документы и автоматическая передача менеджеру ещё не реализованы.
`manager_review` показывается как необходимость проверки, не как состоявшаяся передача.
Клиентская eligibility, выбор утверждённого режима и отправка сообщений отсутствуют.

## Данные и поведение формы

- При первой анкете используется последняя принятая версия набора `kg_entry` и последняя
  история этого контакта, если она есть. Если импорта нет, показывается пустое состояние.
- Последующие версии сохраняют закреплённые KB/history предыдущего снимка. UI пока
  не выбирает другую версию источника/истории; изменение требует отдельного domain flow.
- GET проверяет snapshot, accepted import, projection и history integrity. Записи при
  открытии нет. Ошибка источника/БД показывает недоступность, а не пустую успешную анкету.
- Новая проверка датируется текущим днём Бишкек, дата выданной формы закреплена подписью.
  Дата старого отчёта показана отдельно. При retry используется дата исходной формы.
- Поля профиля заменяются целиком. При выборе «За рубежом» текущие сведения пребывания
  КР удаляются **из новой версии**, старая сохраняется. При известном основании кроме
  визы убирается старый тип действующей визы. Это не удаление истории поездок.
- Дополнительные condition facts читаются из подписанной исходной версии на сервере;
  браузер не может подставить их. Их можно явно исключить из новой версии чекбоксом;
  редактор таких условий в этот этап не входит.
- Повтор отправки использует прежний ключ; другая вкладка с устаревшей ревизией получает
  409 и свои введённые ответы. Нельзя незаметно перезаписать новую версию.
- После неопределённого commit форма сохраняет ключ/поля для повторной отправки. Если
  дополнительное чтение БД тоже не удалось, fallback показывает только введённые клиентом
  формы значения; следующая запись всё равно заново проверяет реальные источники.

## Доступ и включение

Новый env-флаг `ADMIN_KG_ENTRY_ENABLED=false` по умолчанию, проброшен в Compose.
Для локального стенда нужна существующая схема до `e5_qualification_0016` и принятый
импорт знаний KG; этот этап новой миграции или автоматического импорта не добавляет.
Также требуется существующий `ADMIN_WORKDAY_ENABLED`; сохранение дополнительно требует
`SERVICE_CASES_ENABLED`. Новый флаг является env-gate, не тумблером интерфейса.
Изменения production env/включение/выкатка отдельно не выполнялись.

Права **не расширены**: только named full-admin через существующую аутентификацию панели.
Обычный визовый менеджер также получает отказ, даже для своей услуги. Владелец должен
определить разрешённый менеджерский scope до расширения доступа. Туровые/билетные услуги
и чужой qualification id под данным контактом недоступны.

Контакт, автор, источник, история и базовая ревизия не выбираются произвольным POST:
служебные поля защищены session-bound HMAC, включающим login, case, contact, base id,
revision, knowledge version, history, as_of и request key; CSRF проверяется отдельно.
Contact берётся из service case; её contact/product bindings неизменяемы штатным доменом.
Флаг OFF и отсутствие прав проверяются до доменной БД.

Только URL-encoded форма: максимум 16 KiB, 70 параметров, известные имена и ограниченная
длина; дубликаты запрещены кроме списка гражданств. Jinja экранирует значения, ошибки
и логи не содержат введённый payload. Ответы с содержимым анкеты имеют `Cache-Control: no-store`.
Существующие правила срока сессии/отзыва ролей панели не меняются этим этапом.
