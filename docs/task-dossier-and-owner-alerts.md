## 1. Зачем — с цифрами

**Блок 1-3.** Заказчик по турам (Даулет) требование сформулировал так: бот ведёт карточку
сам, менеджер лишь сверяется с клиентом, когда тот физически пришёл в офис. Сегодня это
не выполняется:

* замер 21.08 по боевым туровым каналам: из 11 диалогов за 6 часов после подключения QR
  **8 перехвачены менеджером** (5 из 5 у Адеми, 4 из 6 у Айсины);
* `sync_dossier` выходит первой строкой на `intercepted` → в этих 8 карточках досье
  не появится никогда;
* за август по турам 333 диалога, лид заведён у 326 — то есть карточки есть, а сводки
  в них нет.

**Блок 2 — отдельный дефект, найден тестом 21.08.** Проверка `not remembered and comments
and not _dossier_ours(...)` пропускает запись, если бот когда-либо писал в поле. Прогон:
менеджер правит карточку после бота → следующее обновление **затирает правку**. Сейчас не
стреляет только потому, что перехваченные диалоги вообще не обновляются; блок 1 снимает
это прикрытие и открывает дефект. Поэтому блоки 1 и 2 идут одной задачей, порознь нельзя.

**Блок 3.** Живой прогон `render_dossier` на лиде 186261 даёт строку `Состав: 4 · 7, 10`.
Менеджер, сверяющий заказ с пришедшим клиентом, не обязан догадываться, что это четыре
туриста и дети семи и десяти лет. Сводка, которую надо расшифровывать, свою работу
не делает.

**Блок 4.** Заказчик по визам (Гриша, telegram `434859857`) попросил уведомлять его
самого о платежах и об отвале каналов — «так проще». Сегодня `ops_alert_chat_ids`
содержит один id (Алана). Мониторинга баланса OpenRouter нет вообще: 21.08 бот замолчал
на исходе баланса, узнали постфактум. Остаток на момент ТЗ — $21.16 при расходе
$0.50/сутки; с ожившими туровыми каналами расход вырастет (туровый ход дороже визового
примерно вдесятеро — контекст длиннее).

## 2. Границы — чего НЕ делаем

* **Не трогаем `advance()`** и логику стадий — это сделано в `99a798a`.
* **Не заводим отдельное поле** в карточке Битрикса (`UF_*`). Обсуждалось как более
  чистое решение, но требует настройки на стороне портала заказчиком. Остаётся на потом;
  блок 2 закрывает риск логикой.
* **Не пишем досье в терминальных статусах** и не меняем `TERMINAL_STATUSES`.
* **Не трогаем зеркало реплик** (`bitrix_mirror.py`) — оно работает.
* **Не добавляем алерт «баланс кончился совсем»** отдельно от порогового: одного сигнала
  с запасом по дням достаточно, второй будет шумом.
* **Не строим свою историю расходов** — OpenRouter отдаёт `usage_daily`/`usage_weekly`.
* **Не даём заказчику доступ в админку** — только уведомления в Telegram.

## 3. Точка врезки

### Блок 1-2 — `app/integrations/crm/bitrix_pipeline.py`, `sync_dossier` (стр. 157-182)

Сейчас:

```python
if not lead_id or getattr(conv, "intercepted", False):
    return False
...
remembered = bool(getattr(conv, "bitrix_dossier_by_bot", False))
if not remembered and comments and not _dossier_ours(comments) and not _legacy_ours(comments):
    return False
```

Должно стать (смысл, не буквальный код):

1. `intercepted` перестаёт быть безусловным выходом — проверяется вместе с новым флагом
   `dossier_when_intercepted_enabled`, ровно как `_catchup_enabled()` в `advance()`.
   Держать один стиль: рядом уже есть образец, введённый `99a798a`.
2. Владение полем определяется **только по текущему содержимому**: пусто, наше досье
   (`_dossier_ours`) или легаси (`_legacy_ours`) → пишем. Всё прочее → выходим.
   Флаг `bitrix_dossier_by_bot` из условия убрать; само поле оставить — его читает
   догоняющий проход.

Почему здесь: это единственная точка записи в `COMMENTS` лида. Правка в вызывающем
`_advance_and_sync` не годится — досье пишется ещё и из `catchup_once`.

### Блок 3 — `render_dossier` (стр. 101-131), только строка «Состав»

Сборка `values` через `' · '.join(...)` остаётся для остальных меток. Для состава —
отдельная функция `_compose_line(q) -> str`, склеивающая по-русски:

* `tourists`/`adults` → `N турист/туриста/туристов` (склонение по числу);
* `children_ages` → `ребёнок N лет` / `дети N и M лет` / `дети N, M и K лет`;
* `companions` и словесные значения — как есть, через запятую;
* нечисловое значение `tourists` (клиент написал «мы вдвоём») — отдаём как есть,
  не пытаясь склонять.

Остальные метки не трогаем: `Направление: Турция · Анталья` меняем на запятую только
потому, что это одна сущность (страна и курорт), а не два разных факта.

### Блок 4 — три места

1. `app/config.py`: `ops_alert_chat_ids` уже список — заполняется из `prod.env`.
   Новые настройки: `openrouter_balance_check_enabled`, `openrouter_balance_min_days`,
   `bitrix_health_enabled`, `bitrix_health_confirm_ticks`, `owner_reminder_hours`.
   **Каждая обязана быть дописана в `environment:` `docker-compose.yml`** — иначе из
   `prod.env` в контейнер не попадёт и молча возьмётся дефолт (шрам `475e2f7`).
2. Новый модуль `app/core/balance_guard.py` — по образцу `wappi_health.py`:
   чистая функция `decide(now, credits, state, cfg) -> list[str]` + тонкая обёртка,
   дёргающая `GET https://openrouter.ai/api/v1/credits`. Ответ:
   `{"data":{"total_credits":106,"total_usage":84.84}}`, остаток — разность.
   Скорость расхода берём из `GET /api/v1/auth/key` (`usage_daily`, `usage_weekly`);
   дней остатка = остаток / max(usage_daily, usage_weekly/7, минимальный пол).
3. Проверка Битрикса — в существующий тик `wappi_health.tick()` не пихать; отдельная
   функция в `balance_guard` или новый `app/core/crm_health.py`: вызов
   `crm.status.list` (дешёвый, уже используется), N подряд ошибок → тревога.

Регистрация тумблеров в `FEATURE_FLAGS` (`app/admin/router.py`) обязательна для всех
новых флагов — иначе переключить без деплоя нельзя.

## 4. Калибровка — сколько сообщений получит человек

Закон 5 `venom-v2`: частота измеряется, а не обещается. Replay по логам невозможен —
Redis-состояние сторожа пусто, логи контейнера обрезаны рестартом 21.08. Поэтому считаем
по наблюдаемым событиям августа и фиксируем как оценку, подлежащую перепроверке через
неделю после включения.

| Повод | События за август | Сообщений при нынешних порогах |
|---|---|---|
| Разлогин Wappi | 2 (Айсина 11.08, Адеми 15.08) | первое + напоминание раз в сутки, пока лежит → **16** (каналы стояли 10 и 6 дней) |
| Подписка Wappi | 3 профиля | до 5 на профиль (окно 5 дней, cooldown сутки) → **до 15** |
| Баланс OpenRouter | 1 (21.08) | 1-2 при пороге в днях |
| Битрикс недоступен | 0 подтверждённых | 0 |

Итого при простом «добавить второго получателя» Гриша получил бы **порядка 30 сообщений
в месяц**, из них 16 — повторы про один и тот же лежащий канал. Закон 5 прямо говорит:
шумного сторожа выключают, и тогда он хуже отсутствующего.

**Поэтому: заказчику напоминания идут реже, чем Алану.** Настройка `owner_reminder_hours`
(дефолт 72): первое сообщение о поводе уходит всем получателям сразу, повторные — Алану
по нынешнему суточному cooldown, заказчику не чаще раза в трое суток. Оценка при этом:
2 разлогина × (1 + 2 напоминания) + 3 подписки + 1 баланс ≈ **10 сообщений в месяц**.

Формат для заказчика — что человек с этим СДЕЛАЕТ, а не что случилось:

```
Канал Frunze Travel (WhatsApp) отключился 15.08 в 10:18.
Клиенты в него не попадают. Нужно отсканировать QR с телефона,
на котором стоит этот WhatsApp: Wappi → профиль FrunzeTravel2 → QR.
```

```
OpenRouter: осталось $4.10 — при нынешнем расходе хватит примерно
на 8 дней. Когда закончится, бот перестанет отвечать клиентам.
Пополнить: openrouter.ai → Credits.
```
