## 1. Зачем

**Учёт по турам не существует.** Проверено на живом портале 17.08.2026:

| Факт | Число |
|---|---|
| Продаж по отчёту таргетологов, 01.07–12.08 | **158** на 13 152 472 KGS |
| Сделок в Битриксе за тот же период | **7**, туровая одна и та с названием «фио» |
| Туровых лидов не в статусе `NEW` | **0** |
| Вызовов `crm.update_stage`, ушедших в никуда | все — `bitrix_stage_map` пуст |

То есть бизнес продаёт, а CRM об этом не знает. Причина не в лени менеджеров: чтобы
продажа попала в учёт, нужно **три действия** — конвертировать лид, выбрать воронку,
вписать сумму. Задача — свести это к **одному касанию**: менеджер ставит «Подписан»,
всё остальное делает код.

Вторая половина задачи — довести карточку до состояния, в котором это касание возможно:
сейчас карточка пустая, и менеджеру нечего подтверждать. Его единственная озвученная
жалоба (встреча 06.08) — «карточка не очень всегда понятна».

⚠️ Отдельно и вне этой задачи: у туровых Открытых линий стоит раздача `all` («всем
сразу»), у визовых — `evenly` («по очереди»). Именно поэтому визовые отвечают из
Битрикса (165 ответов через `outgoing_message_api` против 9 с телефона за сутки), а
туровые — с телефона. Это настройка портала, кодом не решается.

## 2. Границы задачи

**Делаем:** движение стадии лида ботом, досье в карточке, обратное чтение статусов,
создание сделки по подтверждению менеджера.

**НЕ делаем в этой задаче:**

- не трогаем `bitrix_mirror.py` в части выбора карточки и выгрузки истории — там уже
  разобранная логика с локом и ожиданием лида Открытой линии, она работает;
- не меняем настройки Открытых линий через API (`imopenlines.config.update` нам
  доступен, но это чужой портал и живые люди — только по отдельному решению);
- **не мигрируем старые карточки**: ни задним числом стадий, ни массовой заливки
  истории. Включение по событию, см. §7;
- не создаём Deal ни в каком другом месте, кроме подтверждения менеджером;
- не трогаем промпты, TourVisor, STT, календарь;
- не читаем вебхуки от Битрикса (`/webhook/bitrix` не трогаем) — обратная связь идёт
  опросом, чтобы не зависеть от настройки портала.

## 3. Флаги и настройки

| Флаг (БД, булев) | Дефолт | Смысл |
|---|---|---|
| `bitrix_pipeline_enabled` | **False** | глобальный; снятый = аварийный рубильник для всех ботов |
| `bitrix_pipeline_enabled:<bot_id>` | глобальный | пер-ботовый — им и обкатываем на одном канале |
| `bitrix_autodeal_enabled` | **False** | создаёт сделку по `CONVERTED`; выключен = dry-run, только метрика |

Пер-ботовый флаг обязателен и читается тем же способом, что уже работающий
`stt_enabled:<bot_id>`. Без него обкатать конвейер можно только на всех каналах сразу,
а первый прогон делается на телеграм-боте `frunze_tours_tg` — он клиентский по
сценарию, но живого трафика там нет (см. `docs/HANDOVER-ACTUAL-2026-08-03.md` §7).

Оба зарегистрировать в `FEATURE_FLAGS` (`app/admin/router.py`) — иначе тумблера в
админке нет и без деплоя не переключить.

| Настройка | Значение для прода |
|---|---|
| `bitrix_stage_map` | `{"qualified": "UC_S0NTF8", "offer_sent": "UC_PNSIIB", "touch_1": "UC_1I1YV0", "touch_2": "UC_T9AEO4"}` |
| `bitrix_deal_category_id` | `27` |
| `bitrix_deal_stage_id` | `C27:NEW` |

Стадии портала выгружены живьём (`crm.status.list`, `crm.dealcategory.stage.list`):

```
NEW → UC_S0NTF8 Выявление потребностей → UC_Y4VY7B Переписка/Недозвоны →
UC_1I1YV0 1 касание → UC_T9AEO4 2 касание → UC_A492DB 3 касание →
UC_PNSIIB Предложение отправлено → UC_R8BD0W Не квалифицированный →
CONVERTED Подписан → JUNK Некачественный

Сделки, категория 27 «FrunzeTravel»:
C27:NEW Оплата получено → C27:EXECUTING → C27:PREPARATION → C27:FINAL_INVOICE →
C27:UC_0BLN99 Вылетел → C27:WON / C27:LOSE
```

⚠️ `manager_handoff`, `office_consultation`, `visa_scoring` **намеренно не мапятся**:
стадии «передан менеджеру» в портале нет, а любая замена (например
«Переписка/Недозвоны») означала бы, что мы двигаем карточку в момент, когда её берёт
человек. Существующие вызовы `update_stage` с этими ключами продолжают тихо
пропускаться, как сейчас.

## 4. Где врезаться

**Стадия `offer_sent`** — `app/agent/runner.py`, функция `_attach_tour_cards` (строка
249), ветка, где `cards` непусты и блок реально приклеивается к ответу. Причина: это
единственное место, где подборка гарантированно уходит клиенту. Ставить стадию по факту
поиска нельзя — модель за ход ищет 2–3 раза, и часть результатов до клиента не доходит
(этим уже обжигались, коммит `7168163`).

**Стадия `qualified`** — там же в `runner.py`, после `state.qualification.update(...)`.
Условие «квалификация собрана» реализуй как отдельную функцию `_is_qualified(state)`:
для туров — направление/страна **и** даты **и** количество человек; для виз — страна
**и** цель поездки. Пустые строки и `None` не считаются.

**Досье** — вызывается там же, где и стадия: одним вызовом после `advance`, чтобы не
плодить обращения к порталу.

**Обратное чтение** — новая фоновая джоба в планировщике, период 10 минут.

Всё, что уходит в портал, вызывается **через `fire()`-подобный фон** по образцу
`bitrix_mirror.fire`: ответ клиенту не должен ждать Битрикс.

## 5. Правила движения стадии

Реализуй в `app/integrations/crm/bitrix_pipeline.py`.

1. **Только вперёд** по `STAGE_SEQUENCE`. Стадия «раньше» текущей — не отправляется.
2. **Человек главнее навсегда.** Перед каждым движением читаем `STATUS_ID` карточки.
   Если он не равен тому, что бот ставил последним (`conv.bitrix_stage_by_bot`) —
   значит карточку двигал человек. С этого момента бот **не двигает эту карточку
   никогда**, даже если дальше придёт «правильная» по порядку стадия.
3. **Терминальные статусы неприкосновенны**: `CONVERTED`, `JUNK`, `UC_R8BD0W`. Бот их
   не ставит и в них не пишет.
4. **Перехваченный диалог** (`conv.intercepted`) — не двигаем.
5. **Нет `bitrix_lead_id`** — молча выходим (карточка ещё ищется, это норма).
6. Флаг снят или карта пуста — ноль обращений к порталу.

Каждое движение логировать: `conv_key`, откуда, куда, причина пропуска.

## 6. Досье

**Пишется в поле `COMMENTS` лида** через `crm.lead.update`, а не комментарием в
таймлайн. Причина проверена на портале: доступны только
`crm.timeline.comment.get/list/fields` — обновить комментарий нечем, и досье плодилось
бы копией на каждый ход.

Состав: направление, бюджет, даты, состав (взрослые/дети), что бот уже предложил
(ссылка на страницу `/t/{slug}`, если есть), ссылка на диалог в нашей панели, время
последнего сообщения. Одним экраном, без «воды».

Первая строка — маркер `DOSSIER_MARKER` (константа модуля, например `🤖 Бот:`).

**Источник фактов — состояние хода (`DialogState.qualification`), а не карточка
диалога.** Проверено на проде 17.08: `conversations.qualification` заполнена у **28
диалогов из 322**. Живые данные лежат в `DialogState` (Redis, TTL 7 дней), в панель
попадают не всегда. Досье, собранное по `conv`, было бы пустым в девяти случаях из
десяти. Поэтому `sync_dossier` принимает `qualification` явно, а `None` означает
«взять из conv» — это путь для фоновых вызовов, где состояния уже нет.

**Предохранитель:** если `COMMENTS` непуст и написан человеком — не трогаем никогда и
возвращаем `False`.

⚠️ **Своим считается не только текст с маркером.** Живая карточка 186199 (17.08):
в `COMMENTS` лежит `destination: Турция\nregion: Анталья\ndeparture_city: Бишкек\n…` —
это наш же `_format_qualification` из `create_lead`, маркера там нет. Правило «нет
маркера → не трогаем» заморозило бы досье во всех карточках, созданных ботом. Считать
своим текст, который целиком состоит из строк `<ключ>: <значение>` с ключами из набора
`_format_qualification`. Заодно добавить маркер и в `create_lead`, чтобы новые карточки
опознавались однозначно.

## 7. Обратное чтение и сделка

Джоба `read_back_once()`:

1. Берёт диалоги, у которых есть `bitrix_lead_id` **и было сообщение после включения
   фичи** (см. ниже), пачками, не более N за тик.
2. Читает `STATUS_ID` карточки. Ничего не пишет в портал, пока не выполнены условия §7.4.
3. `CONVERTED` → фиксируем продажу у себя: `outcome = "won"` на диалоге. Это и есть
   цифра для месячного отчёта.
4. При `bitrix_autodeal_enabled = True` — создаём сделку: `CATEGORY_ID = 27`,
   `STAGE_ID = C27:NEW`, `TITLE` по клиенту, `OPPORTUNITY` из подборки/бюджета,
   `ASSIGNED_BY_ID` — тот же, что у лида, плюс ссылка на диалог. Id сделки пишем в
   `conv.bitrix_deal_id`. **Повторный тик сделку не создаёт** — проверка по этому полю.
5. При выключенном флаге — только счётчик «создали бы N сделок» в лог и метрику.

**Включение по событию, а не по дате создания диалога.** Диалог, заведённый до выкатки,
входит в конвейер при первом новом сообщении. Отсечка по дате создания недопустима:
половина туровых обращений — возвращающиеся клиенты, они навсегда остались бы в старом
режиме. Массовой обработки старых карточек нет ни в каком виде.

Счётчики за сутки: `checked`, `moved`, `frozen_manual`, `dossier_written`,
`dossier_skipped_human`, `won`, `deals_created`, `deals_dry_run`, `errors`.

## 9. Критерий готовности

- Гейт зелёный целиком, существующие тесты зелёные, `prod_traps_check` 0 ERROR.
- Оба флага сняты по умолчанию → **после деплоя в портале не меняется ничего**.
- На тестовом диалоге при включённом `bitrix_pipeline_enabled` видно: карточка уехала
  в «Выявление потребностей», затем в «Предложение отправлено», в поле комментария
  лежит досье, в логе — счётчики.
- Ручной перенос менеджером замораживает бота по этой карточке (проверить руками на
  одной живой карточке до включения на всех).
- `bitrix_autodeal_enabled` остаётся выключенным до отдельного решения Даулета —
  выкатываемся в dry-run и смотрим счётчик «создали бы».
