# E5-03A — проверочные расчёты дней пребывания

07.10.2026. CRITICAL / solo, **PARTIALLY_READY** до independent review/final audit.
Локальный этап CALC-02: арифметика по явно заданному сценарию и примеры для утверждения.
Хранение истории, производственный календарь CALC-03 и клиентский калькулятор ещё не подключены.

## Источник и ограничение

Прочитана физическая стр.24 оригинального PDF, раздел 2.9; SHA проверена:
`141b9e1e570c916aab65f3dc40e927cc61ef182e1d155b997a5123091e36cca2`.
В техническом ТЗ CALC-02 требуется проверять окно **на каждом дне** плана, учитывать
все интервалы и утверждать включение дней/смену основания на эталонах до выпуска.
Три параметра `KG.RULE.COUNT_ENTRY_DAY`, `COUNT_EXIT_DAY`, `WINDOW_ANCHOR` в текущем
bundle всё ещё `decision_pending`, `value=NULL`. Код не заполняет и не утверждает их.

`StayDayReview` принимает validated bundle, явно указанный кандидат `KG.VF.*`, snapshot
поездок и proposed policy. `days/window_days` берутся только из typed value этого кандидата.
Blocked evidence не становится действующим значением. NULL value, страна вне кандидата
или отсутствующая policy дают `needs_input`, без арифметики.

Даже полный/confirmed вход и численно успешный сценарий всегда возвращают:
`may_quote=false`, `publication_approved=false`, `entry_eligibility_evaluated=false`,
`selected_regime=NULL`, `exact_remaining_days=NULL`. Это не результат ЕСУВМ и не
определение применимости нормы на дату поездки. Проверка SHA подтверждает источник,
а не юридическую актуальность. Входной флаг confirmed сам по себе не доверенная авторизация.

## Вход и арифметика

`app/knowledge/stay_schema.py`: строгий `kg-stay-review-input/1` без дополнительных полей.
Один snapshot содержит as_of, полноту истории, актуальные interval records, planned trip,
rule_unit_id и policy (либо NULL). Полей contact/phone/passport number/готовых счётчиков нет.
История здесь уже должна быть отобрана без superseded записей; persistence/adaptor ещё нет.

| Поле / ситуация | Поведение |
|---|---|
| policy | status=proposed; оба count_entry_day/count_exit_day заданы явно, без defaults; anchor=each_day_backward_inclusive; timezone=Asia/Bishkek |
| Закрытая поездка | Исторические entry/exit не позже as_of; exit >= entry. Исключение границы сдвигает соответствующий конец на 1 день |
| Однодневная поездка | Даёт один день, только если включены обе границы; иначе пустой интервал |
| Дубли / пересечения | Объединение календарных дней, один день учитывается один раз. Разные записи с одинаковыми датами допустимы, одинаковые IDs — ошибка |
| Открытая поездка | Не больше одной; reported history обрезается по as_of включительно: это не выезд, exit exclusion здесь не применяется |
| Продолжение открытой поездки | trip.mode=continue_open, start_date=as_of; считаем от настоящего въезда до proposed end, без нового въезда в as_of |
| Новый въезд при незакрытой поездке | needs_input; дата выезда не придумывается |
| Поздняя закрытая поездка поверх открытой | Ошибка противоречивой истории. Выезд и повторный въезд в одну дату допускаются, общий день не удваивается |
| Разные основания / паспорта | Не фильтруются молча; flags требуют проверки. Сценарий показывает присутствие по указанным датам, не подтверждённые безвизовые дни |
| Неизвестная полнота / неподтверждённые записи | Явные findings; математический результат только для предоставленных данных, не точный остаток и не гарантированная нижняя граница фактического пребывания |

Все даты — уже локальные календарные даты Asia/Bishkek; timestamps не принимаются.
Для каждой даты D плана окно: `[D − window_days + 1, D]`, включительно с обеих сторон.
После объединения интервалов prefix sums и бинарный поиск считают длину пересечения
с окном. Високосные дни/конец года учитывает календарь Python, без приближения месяц=30 дней.

`daily` содержит границы окна, reported_history_days, scenario_presence_days,
scenario_headroom=`limit − presence` и сравнение с лимитом. **Headroom одного окна
не является будущим разрешённым сроком.** first_exceeded_date относится только к
проверяемому плану. Исторические нарушения до него и дата следующего разрешённого
въезда не вычисляются. Нет придуманного порога «пограничности»/автоэскалации.

`counted_intervals.record_ids` сохраняет всех участников объединённого сегмента,
не утверждает, что каждая запись доказывает каждый день сегмента. План нового въезда
обозначен зарезервированным `@planned_trip`; входные IDs не могут содержать `@`.

Технические пределы: 1000 записей, 730 календарных дат плана, окно до 3660 дней;
underflow за 0001-01-01 отклоняется. Это пределы реализации, не правовые лимиты.
Integral JSON numbers вроде 30.0 допускаются действующей JSON Schema и нормализуются
к целым перед календарной арифметикой. Дробные/нечисловые значения отвергает bundle preflight.

## Воспроизводимость и запуск

Алгоритм `kg-stay-arithmetic/1`, source_hash, bundle_hash, rule ID, proposed policy,
input_hash и calculation_hash связывают результат с входом. История сортируется по ID
перед hashing; перестановка записей не меняет результат. Файлы/БД калькулятор не пишет.
Для воспроизведения сохранить исходный request и соответствующий bundle по правилам
будущего защищённого workflow; один hash входные данные не восстанавливает.

```powershell
python -X utf8 scripts/review_kg_stay_days.py knowledge/kg_entry/draft-v1.1 --source "../Kyrgyzstan-visa-knowledge-base-v1.1.pdf" --request tests/fixtures/kg_entry/synthetic_stay_review.json
python -m pytest tests/test_kg_stay_days.py tests/test_kg_conditions.py tests/test_kg_country_index.py tests/test_kg_entry_validation.py -q
```

CLI проверяет фактический source hash, выводит JSON; ok=true означает корректный review
request, в том числе с needs_input, а не разрешение въезда. При ошибке код обезличен.
Никаких .env/DB/network imports, runtime endpoint, слотов или изменений общего календаря задач.
Будущий production adapter должен брать поездки из authoritative `stay_intervals`, не из slots.

Машинный файл: `tests/fixtures/kg_entry/stay_review_examples.json`, **proposed_not_approved**.
Ниже явно предполагается включение обоих пограничных дней. Годы/даты синтетические;
пример 2024 проверяет календарь, не действие нормы в 2024 году.

| Пример | История / план | Ожидаемая арифметика при предложенной policy |

| RUS_60_PLUS_31 | Та же история; план до 09.04 | 91 на 09.04 |

математическая величина, не режим из PDF.
