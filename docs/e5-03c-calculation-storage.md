# E5-03C — хранение истории и проверочных расчётов

09.10.2026. CRITICAL / solo, локальная реализация; **PARTIALLY_READY** до независимых
review/final audit. Этот этап сохраняет версии истории, календарей и результаты CALC-02/03.
HTTP, UI, LLM и рабочий бот пока не подключены. Все проверки используют synthetic данные.

## Данные и миграция

`e5_calculation_0015` после `e5_projection_0014`: семь новых таблиц DomainBase,
без ALTER прежних таблиц, начального наполнения и изменения активных версий знаний.

| Таблица | Назначение |
|---|---|
| stay_histories | Неизменяемый полный снимок истории contact, revision, previous_id, cutoff, полнота |
| stay_intervals | Типизированные интервалы конкретного снимка, основание и подтверждение |
| work_calendars | Неизменяемый draft-календарь KG на год/версию, исходный документ и hash |
| work_calendar_days | Праздники и переносы конкретной версии календаря |
| entry_calculations | Запрос, фактический input, output, источники, окружение и hashes |
| entry_calculation_intervals | Связь расчёта с интервалами именно его версии истории |
| entry_calculation_calendars | Связь расчёта с выбранными версиями календарей |

Уточнение [исходного проекта](e5-02-slots-schema.md): исправление создаёт **новый полный
снимок истории**, а не меняет `superseded_by` прежнего интервала. Это сохраняет вместе
cutoff, полноту, даты и подтверждения, использованные старым расчётом. FK связывают
историю с contact, а интервалы расчёта — одновременно с расчётом и его историей.
Одна история допускает не более одного открытого интервала. Закрытые пересечения
и дубли с разными ref передаются калькулятору для объединения.

Downgrade сначала проверяет все семь таблиц. Если хотя бы одна заполнена, операция
отклоняется до удаления таблиц. Offline downgrade запрещён. Автоматической очистки нет.

## Контракт Python

`app/domain/entry_storage.py`: `save_stay_history`, `read_stay_history`,
`import_work_calendars`, `read_work_calendars`.
`app/domain/entry_calculations.py`: `save_calculation`, `read_calculation`, `replay_calculation`.

Каждый вызов сначала проверяет существующий named full-admin guard knowledge import.
Actor должен поступать из доверенной серверной аутентификации. SYSTEM_ACTOR, bot,
обычный manager, пустое имя, словарь с заявленными правами не допускаются. Это внутренний
API для проверки; политика доступа менеджеров к клиентам требует отдельного этапа.
Сервис получает AsyncEngine, открывает собственную сессию и атомарную транзакцию.

`save_stay_history(engine, actor=..., contact_id=..., expected_revision=0,
request_key="history-1", document=...)` принимает строгий документ:

```json
{
  "format": "kg-stay-history/1",
  "as_of": "2026-10-01",
  "history_complete": null,
  "intervals": [{
    "ref": "synthetic-visit",
    "entry_date": "2026-09-20",
    "exit_date": "2026-09-22",
    "basis": "visa_free",
    "passport_country": "RUS",
    "passport_ref": null,
    "evidence": "client_statement",
    "confirmed": false
  }]
}
```

Это вымышленные данные. `passport_ref` — null либо непрозрачный идентификатор из 32
строчных hex-символов, не номер паспорта. Имена, телефоны, паспортные номера и свободные
заметки схемой не принимаются. Оператор отвечает за непрозрачность ref/request_key:
формальная проверка строки не определяет, закодировал ли оператор личные данные.
Подтверждение записывает имя администратора и UTC-время снимка; client_statement
не может быть confirmed. Даты позже cutoff, неверные даты, два открытых интервала
и повтор ref отклоняются. Полнота true/false/null остаётся явным заявлением оператора.

Первая revision ожидает 0, следующая — текущую revision. Несовпадение возвращает
`stale_history_revision`; автоматического объединения правок нет. Одинаковые
contact/request_key и нормализованный payload возвращают прежнюю запись с reused=true,
другой payload — конфликт. Идемпотентный повтор проверяет целостность старого снимка.
После неопределённого результата commit возвращается
`commit_outcome_unknown_retry_same_request`: повторить **тот же ключ и payload**.
Не придумывать новый ключ. Исключения не содержат SQL, DSN и исходный payload.

Для stay расчёта передаются kind="stay", contact_id, knowledge_version_id, history_id,
request_key и request с **только** rule_unit_id, trip, policy, passport_ref.
Поля trip/policy описаны в [E5-03A](e5-03a-stay-days.md). history, confirmed, cutoff
и history_complete строятся исключительно из сохранённой истории. Одинаковые известные
passport_ref дают continuity=same, разные — changed, неизвестный ref — unknown.
Для deadline передаются kind="deadline", явный список calendar_ids и документ
[E5-03B](e5-03b-deadlines.md); history_id запрещён. Две версии одного года выбирать нельзя.

Календарь импортируется коллекцией `kg-work-calendars/1`. Все годы записываются атомарно,
существующий год/версия переиспользуется только с тем же содержимым. Статус всегда draft.
Отсутствие или provisional нужного года сохраняет blocked результат без вычисленной даты.

## Воспроизводимость и ограничения

Расчёт ссылается на конкретную принятую knowledge version, полный history snapshot
и явные calendar versions. Проверяются hashes исходных снимков и типизированные проекции.
Сохраняются input/output, исходный запрос, FK источников и identity алгоритма/кода,
Python, jsonschema и TZif Asia/Bishkek для deadline. Смена текущей истории или календаря
не переписывает прошлый результат. Читать сохранённый результат можно после изменения
окружения; replay в другом окружении возвращает `replay_runtime_changed`. Для воспроизведения
нужны прежние код/окружение и источники. Несовпадение пересчитанного результата также
отклоняется. Hash обнаруживает повреждение, но не является подписью против DBA, который
может переписать одновременно данные и контрольные суммы.

ORM запрещает изменение/удаление снимков и вложенного JSON; typed child должен совпадать
с parent snapshot. Прямой SQL администратора остаётся вне этой границы. Сервисы проверяют
целостность при чтении и replay, не исправляя данные автоматически.

Все результаты review_only: exact_remaining_days/exact_deadline=NULL, may_quote=false.
Исходные 208 единиц PDF не менялись; нормы, официальный календарь и эталоны не утверждены.
История и расчёты в реальной CRM будут персональными данными, даже без номера паспорта.
Сроки хранения/удаление/DEC-06 здесь не утверждались. Production activation и импорт
реальных данных требуют отдельного решения, PG16 runtime и независимой проверки.

## Локальная проверка

```powershell
python -m pytest tests/test_entry_storage.py tests/test_entry_storage_migration.py -q
python scripts/rehearse_kg_calculations.py --db runs/e5-03c-demo.sqlite3
```

CLI принимает только **новый локальный SQLite-файл** и отказывается открывать существующий.
Он мигрирует пустую БД, импортирует synthetic fixtures, сохраняет историю, два календаря,
два расчёта и проверяет replay. Ambient DSN не используется. Итоговый JSON содержит
только счётчики и synthetic сценарии: 6 дней, срок 08.10.2026, точные клиентские значения NULL.
Повтор запуска требует нового disposable filename; созданная БД не предназначена для production.
