## Что здесь было точкой входа (до v4)

Здесь лежит протокол, по которому работает AI-команда на этом проекте. Начали использовать
29.09.2026.

```
ai-protocol/
  README.md                                    ← этот файл: приоритеты и проектные требования
  AI_ENGINEERING_TEAM_PROTOCOL_v2_UNIVERSAL.md ← универсальный протокол v2.0, копия без правок
```

Универсальный протокол хранится **как есть**, чтобы его можно было сверить с оригиналом и
обновлять целиком. Всё проектное — в этом README, а не внутри него (так требует §6 и §56
самого протокола: универсальный документ говорит *как* работает команда, проектный — *что*
за проект).

## Приоритет документов

1. **`ai-protocol/AI_ENGINEERING_TEAM_PROTOCOL_v2_UNIVERSAL.md` — главный.** При расхождении
   действует он.
2. **`docs/protocol.md` — проектное дополнение.** Действует там, где универсальный протокол не
   знает наших деталей: какие у нас скрипты-гейты, какие инциденты чему научили, что именно
   считается доказательством на этом проде. Не архив и не отменён.

Отдельно стоит помнить правило §1.4 универсального протокола: текущий код и текущие
доказательства с прода важнее любого из этих документов. Документ, разошёлся с кодом, —
неправ документ.

## Классы риска: один смысл, два словаря

`docs/protocol.md` говорит S / M / B / C, универсальный протокол — TRIVIAL … CRITICAL.
Это не два разных процесса, а один. Соответствие:

| Наш класс | Класс универсального протокола | Что это у нас |
|---|---|---|
| **S** | TRIVIAL / SMALL | текст уведомления, лог, тест, документация, рефактор без смены поведения |
| **M** | SMALL / NORMAL | несколько файлов, поведение бота для клиента не меняется |
| **B** | IMPORTANT | промпт, воронка, ответ клиенту, дожим, карточки, подача туров |
| **C** | CRITICAL | миграции, деньги и подписки, рассылки, ключи, прод-данные, детекторы с порогами, всё, что пишет человеку само |

Класс называется **до** начала работы. Сомневаешься между двумя — берёшь старший
(§4: «The agent must not lower the verification level merely because implementation is easy»).

## Проектные требования, которых в универсальном протоколе нет

Универсальный протокол требует доказательств, но не знает, чем именно они добываются здесь.
Эти правила выстраданы инцидентами и не отменяются ни одним из уровней:

- **Флаг с дефолтом OFF на всё, что меняет поведение для клиента.** Выкатили код — поведение
  не изменилось; включаем отдельным решением. Ключи — `app/core/flags.py`, переключаются в
  админке, живут в БД. Настройка, которую читает чистая функция из `settings`, флагом в БД не
  включается — ей нужна строка в `prod.env` и рестарт.
- **Деплой на прод — только по прямому слову Алана.** «Почини» деплой не разрешает. Это
  human gate в смысле §21, и он не зависит от класса задачи.
- **`python scripts/prod_traps_check.py --diff-base HEAD` до прода.** Ловит настройки, не
  проброшенные в `docker-compose.yml`, мёртвые настройки и расхождения env. Это наш
  scope/config-валидатор из §25.
- **Детекторы калибруются на истории прода, а не на рассуждении.** `scripts/alert_replay.py`
  (тишина каналов), `scripts/watchdog_replay.py` (сбои). Ряд событий восстанавливается из
  логов и из таблицы `messages`. Порог, взятый «по смыслу», трижды подводил в августе.
- **Качество диалогов мерится тренажёром**, а не на глаз: `scripts/run_scenarios.py`.
- **`PROD_HEALTHY` ≠ `PROD_FUNCTIONALLY_VERIFIED`** (§19). После деплоя обязательно вызвать
  изменённую функцию **в боевом контейнере** и показать вывод. `/health` — не доказательство.
- **`scripts/smoke_test.py` по проду не гонять**: он создаёт мусорный диалог через вебхук.
  Прод не используется как площадка приёмочного тестирования (§20).
- **Отчёт заканчивается доказательствами** в форме §27: что / где (файлы, коммит) / чем
  проверено (команда и число) / где проверено (локально, образ, прод) / **что осталось
  непроверенным**. «Работает», «тесты зелёные», «деплой прошёл» — не доказательства.

## Роли — по факту, с командами вызова

Вся команда стоит на этом ПК, поэтому роли исполняются, а не числятся: контекст между
исполнителями не носится руками через браузер. Codex CLI 0.159.0, дефолтная модель
`gpt-6-astra` с `model_reasoning_effort = "xhigh"`; каталог проекта в `~/.codex/config.toml`
помечен `trust_level = "trusted"`. «Астра» и «сол» — модели внутри Codex, а не отдельный продукт.

| Роль по протоколу | Кто у нас | Чем вызывается |
|---|---|---|
| HUMAN OWNER (§2.7) | **Алан** | решения о продукте, приоритеты, доступы, разрешение на прод |
| Architect / Auditor (§2.5) | **Claude Code** (Opus 5) | класс риска, план, ТЗ, разбор данных, отчёт |
| Principal engineer (§2.3) | **Codex**, `gpt-6-astra` | `codex exec -m gpt-6-astra -s workspace-write -C "<каталог>" -`, ТЗ через stdin |
| Independent reviewer #1 (§11) | агент **`codex-reviewer`** (Opus, read-only) | Agent tool; файлы не правит |
| Independent reviewer #2 (§12) | **Codex review**, GPT | `codex review --uncommitted` (рабочее дерево) или `codex review --base <ветка>`. Свой промпт — `codex review -`, но он НЕ сочетается с `--uncommitted`/`--base`: проверено 29.09, CLI отвечает «cannot be used with [PROMPT]» |
| Referee в спорах (§28) | **Codex** на другой модели (`gpt-5.5`) | `codex exec -m gpt-5.5 …` — только когда ревьюеры расходятся |
| Automated validators (§2.6) | `pytest`, `prod_traps_check`, `alert_replay`, `watchdog_replay`, `run_scenarios` | команды в `docs/protocol.md` |
| Director / Requirements (§2.1) | **Алан + Claude Code** | требования ставит Алан, в контракт задачи оформляет Claude Code |

**Когда включается второй ревьюер.** Две независимые головы стоят денег и времени, поэтому
правило по классам, а не «всегда»:

- **C / CRITICAL** — оба ревьюера обязательны: `codex-reviewer` и `codex review`. Смотрят
  дифф, а не отчёт исполнителя (§11).
- **B / IMPORTANT** — один независимый ревьюер, любой из двух.
- **S, M** — по необходимости; на однострочной правке ревью ради ревью обесценивает процесс.

Что даёт роль №2 на практике: 29.09 первый же прогон `codex review --uncommitted` нашёл в
моём диффе голодание очереди — бюджет прогона при фиксированном порядке оставлял хвост
выборки неопрошенным. Ревьюер смоделировал 12 часов и показал, что последний чат не
проверяется ни разу. Дефект исправлен до коммита.

Одна оговорка про его прогон тестов: `codex review` запускает `pytest` по-своему и получает
на Windows около 160 `PermissionError` на временных каталогах. Это известный артефакт
(гонять надо `pytest tests`, а не из корня — см. `CLAUDE.md`), а не регрессия. Верить нашему
прогону, а его тестовый вывод читать с этой поправкой.

Правило §1.2 держится в любом составе: кто написал код, не выносит по нему финальный вердикт
в классе C. Автором кода может быть и Codex, и Claude Code — ревьюер в этом случае берётся
другой.

## Профиль проекта

§6 протокола требует отдельный профиль проекта. Сейчас его роль выполняют:

- **`CLAUDE.md`** — что это за проект, два бренда, карта кода, прод и деплой, внешние системы
  и их подводные камни, рантайм-флаги, бизнес-правила, текущее состояние, что в репозитории
  устарело;
- **`docs/project-journey.md`** — полный путь проекта: хронология, грабли по системам, уроки.
  Читать первым, если садишься за проект впервые;
- **`docs/services-and-models.md`** — внешние сервисы, выбор моделей, деньги, чек-лист «бот
  странный».

Отдельный файл профиля можно вынести позже. Пока его нет намеренно: дублировать факты в
четвёртое место — значит завести четвёртый источник, который устареет первым. Что есть в
`CLAUDE.md`, здесь не повторяется.
